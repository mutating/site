# Единый деплой сайта, API и платформы

Production работает без Docker и Docker Compose. Репозиторий содержит Hugo в
`site/`, API в `platform/api/`, кабинет в `platform/web/` и все проверки в `tests/`. Nginx выбирает приложение по
`server_name`, а единый сервис systemd `throng.service` управляет API, контроллером
и кабинетом. Сервер кабинета отдаёт только интерфейс и публичную конфигурацию. Браузер
обращается прямо к `https://api.mutating.tech/v1`; API разрешает CORS только
для origin кабинета и сам обслуживает браузерные сессии.

| Адрес | Обработчик |
| --- | --- |
| `https://mutating.tech/` | Существующий сайт Hugo |
| `https://api.mutating.tech/` | API и контроллер на `127.0.0.1:8000` |
| `https://platform.mutating.tech/` | Главная кабинета, сервис на `127.0.0.1:8001` |

Используются точные имена двух поддоменов. Для добавления других доменов нужно
добавить их в nginx и сертификат. Базовый адрес API — `https://api.mutating.tech/v1`.
Пример запроса: `https://api.mutating.tech/v1/users`.
На том же поддомене доступны `/agent/v1/*`, `/docs` и `/openapi.json`.
Страницы кабинета доступны без префикса: `/login`, `/profile`, `/organizations` и т. д.
Адреса `/account` и `/account/*` не обслуживаются и возвращают `404` без
перенаправления. Cookie выдаётся API с `Path=/v1/` и привязана к его хосту.
После перехода с прежней схемы пользователям нужно войти заново.
В production логотип кабинета ведёт на `https://mutating.tech/`.

## Публичный TCP-прокси

Схема введена 26 октября 2026 года. Основной сервер и приложения не переносятся:
новый VPS передаёт соединения на фиксированный IP основного сервера.

| Узел | Публичный IPv4 | Назначение |
| --- | --- | --- |
| Основной сервер | `85.204.240.76` | Сайт, API, кабинет, HTTPS/Certbot и Power Cell relay |
| Прокси, тариф NL-Promo | `144.31.78.74` | Ubuntu 24.04; Nginx `stream`; TCP → основной сервер |

IP основного сервера установлен по глобальному DNS через `1.1.1.1` и `8.8.8.8`,
исключив известный адрес нового VPS. В конфигурации прокси он закреплён буквально:
использование `mutating.tech` как upstream создало бы петлю после добавления VPS
в DNS. Изменение адреса основного сервера требует повторного запуска playbook с
новым `proxy_origin_ipv4`.

Прокси управляется только `infra/playbooks/setup-proxy.yml`. Не запускайте на нём
`setup-server.yml`: сайт, Python, Certbot, БД и CI-деплой остаются на основном
сервере. Конфигурация `/etc/nginx/nginx.conf` на прокси целиком генерируется из
`deploy/nginx-stream.conf.j2`; стандартные HTTP sites-enabled не подключаются.
Nginx и `libnginx-mod-stream` устанавливаются через APT, сервис запускается при
загрузке. Перед заменой конфигурации выполняется `nginx -t`, предыдущая версия
сохраняется стандартным backup Ansible. Чужая существующая конфигурация требует
явного `proxy_replace_existing_nginx=true` после её проверки.

| Вход на прокси | Upstream | Обработка на основном сервере |
| --- | --- | --- |
| TCP `80` | `85.204.240.76:80` | HTTP → HTTPS и HTTP-01 проверки Certbot |
| TCP `443` | `85.204.240.76:443` | HTTPS: сайт, API, кабинет и редирект www |
| TCP `8444` | `85.204.240.76:8444` | Power Cell relay: TLS 1.3, HTTP/2 и клиентские сертификаты |

TLS не завершается на прокси; SNI, HTTP Host и клиентские сертификаты проходят
до основного сервера. Поэтому копирование приватных ключей, выпуск сертификатов
на новом VPS и изменения приложения не нужны. PROXY protocol выключен:
для соединений через VPS основной сервер видит IP прокси вместо IP посетителя;
исходный IP есть в `/var/log/nginx/stream-access.log` самого прокси. В журнал
прокси не записываются URL, HTTP-заголовки или содержимое TLS. TCP connect timeout —
5 секунд, тайм-аут бездействия HTTP/HTTPS — 300 секунд, relay — 1 час.
Туннель WireGuard, NAT и IP forwarding не используются.

UFW на новом VPS при первоначальной проверке выключен, nftables/iptables не
содержали правил. Playbook не включает и не сбрасывает firewall. Если UFW уже
активен, он разрешает только нужные TCP-порты, сохраняя существующие правила.
Фильтрация панели хостинга проверяется внешними запросами после настройки.
Публичные listeners прокси — IPv4; AAAA для этих доменов не должны направлять
клиентов на другой, неработающий маршрут.

Запуск из корня репозитория; пароль вводится только в приглашении Ansible:

```sh
LC_ALL=en_US.UTF-8 LANG=en_US.UTF-8 ansible-playbook \
  -i '144.31.78.74,' infra/playbooks/setup-proxy.yml \
  -u root --ask-pass -e proxy_origin_ipv4=85.204.240.76
```

С ключом используйте `--private-key /LOCAL/PATH/TO/KEY` вместо `--ask-pass`;
для пользователя с sudo при необходимости добавьте `--ask-become-pass`.
`proxy_public_ipv4` по умолчанию берётся из `ansible_host` либо IP в inventory;
при подключении по DNS-имени задайте его явно. Тайм-ауты можно переопределить
через `proxy_connect_timeout=5s`, `proxy_idle_timeout=300s` и
`proxy_relay_idle_timeout=1h`.
Пароли/ключи не храните в checkout, параметрах команд или журналах.
Публичный SSH host key прокси закреплён в `deploy/proxy_known_hosts` под
`HostKeyAlias=mutating-proxy`; он получен при первом подключении 26 октября,
без независимой сверки через консоль провайдера. Проверка ключа при последующих
подключениях обязательна. Основной сервер использует отдельный `deploy/known_hosts`.

После применения playbook проверяет origin с VPS, затем HTTPS через фиксированный
IP прокси с машины Ansible. Curl сохраняет доменное имя для SNI и проверки
сертификата; `--insecure` не используется. Проверяются HTML сайта/кабинета,
JSON capabilities API, `/health/ready`, HTTP-редиректы и редирект www.
Для relay проверяются TLS 1.3, ALPN `h2`, валидность сертификата и закрытие
соединения без клиентского сертификата; SHA-256 серверного сертификата через
VPS должен совпадать с сертификатом основного сервера. Полное подключение
устройства с аттестованным клиентским сертификатом этим тестом не выполняется.
Отдельная проверка обычного DNS не подменяет адрес назначения и показывает
фактически выбранный IP. Все запросы идут через текущие маршруты/VPN контроллера;
HTTP proxy из переменных окружения исключается через `--noproxy '*'`.

Повторные проверки и dry run:

```sh
# Работающий прокси, HTTPS и relay; без изменений конфигурации и обычного DNS.
LC_ALL=en_US.UTF-8 LANG=en_US.UTF-8 ansible-playbook \
  -i '144.31.78.74,' infra/playbooks/setup-proxy.yml -u root --ask-pass \
  --tags verify

# Только публичный DNS и HTTPS из текущей сети.
LC_ALL=en_US.UTF-8 LANG=en_US.UTF-8 ansible-playbook \
  -i '144.31.78.74,' infra/playbooks/setup-proxy.yml -u root --ask-pass --tags dns

# Предварительный просмотр повторной конфигурации уже настроенного VPS.
LC_ALL=en_US.UTF-8 LANG=en_US.UTF-8 ansible-playbook \
  -i '144.31.78.74,' infra/playbooks/setup-proxy.yml -u root --ask-pass --check --diff
```

**DNS и переключение.** При начале настройки Cloudflare DNS и Google DNS
возвращали две A-записи, `85.204.240.76` и `144.31.78.74`, для `mutating.tech`,
`api.mutating.tech` и `platform.mutating.tech`, TTL 300 секунд. `www.mutating.tech`
возвращал адреса Cloudflare `104.21.15.6` / `172.67.160.248`, то есть был включён
HTTP-прокси Cloudflare; это отдельный путь, не DNS-only запись нового VPS.
AAAA у трёх основных имён отсутствуют; www публикует IPv6 Cloudflare
`2606:4700:3031::6815:f06` и `2606:4700:3036::ac43:a0f8`.
Авторитетные NS — `deborah.ns.cloudflare.com` и `yoxall.ns.cloudflare.com`.

По решению владельца от 26 октября 2026 года у трёх имён сохраняются оба IP;
ограничение переключения принято. Две A-записи не гарантируют переключение после
зависания TLS. До настройки контроллер с включённым VPN выбирал `85.204.240.76`:
TCP соединялся, TLS завершался тайм-аутом, HTTP-ответа не было. Сам playbook DNS
не меняет. Успешные проверки с `--resolve` подтверждают работу прокси, но не
доступность через обычный DNS. Если позднее потребуется обязательный проход
через новый VPS, альтернативой будет оставить у трёх имён только `144.31.78.74`;
сейчас этот вариант не применяется.

Проверки после настройки 26 октября, с включённым VPN контроллера. В таблице
обычный DNS показан для успешного прогона; последующий прогон выявил описанный
ниже отказ при выборе второго адреса.

| Запрос | Через фиксированный `144.31.78.74` | Через обычный DNS |
| --- | --- | --- |
| `https://mutating.tech/` | 200, HTML, валидный TLS | 200, выбран `144.31.78.74` |
| `https://api.mutating.tech/v1/agent-capabilities` | 200, JSON, валидный TLS | 200, выбран `144.31.78.74` |
| `https://api.mutating.tech/health/ready` | 200, `status=ready` | 200, выбран `144.31.78.74` |
| `https://platform.mutating.tech/` | 200, HTML, валидный TLS | 200, выбран `144.31.78.74` |
| HTTPS www и HTTP трёх имён | 308, ожидаемый Location | В этой проверке не запрашивались |
| TLS relay на 8444 | TLS 1.3 / h2; сертификат совпадает с origin; соединение без клиентского сертификата закрыто | В этой проверке не запрашивался |

Таким образом, новый маршрут проверен полными HTTP-ответами из исходной сети;
прямой origin из неё до настройки зависал после установки TCP. Состояние Nginx
на VPS: `active`, `running`, `enabled`; `nginx -t` успешен.

Повторное полное применение playbook дало `changed=0`: конфигурация и сервис
не менялись; все проверки через фиксированный IP VPS, включая relay, прошли.
Но обычный DNS на этот раз выбрал `85.204.240.76` для всех четырёх запросов:
TCP соединялся, TLS завершался `curl (28) SSL connection timeout` примерно
через 5 секунд. Поэтому playbook честно завершился ошибкой DNS-проверки,
не откатывая исправный прокси. Доступ при опубликованных двух A-записях остаётся
нестабильным; успешный первоначальный прогон не является гарантией переключения.
Dry run `--check --diff` завершился успешно: `changed=0`, `failed=0`.
Основной сервер, DNS и настройки VPN в рамках этой настройки не менялись.

### Повторы запросов кабинета

Общий API-адаптер `platform/web/src/lib/api.ts` использует `reboop`:
чтения `GET`/`HEAD` повторяются при сетевых ошибках и тайм-аутах до успеха
или отмены вызывающим кодом. Лимит одной попытки, включая чтение тела ответа,
— 20 секунд, для GitHub discovery — 90 секунд; паузы составляют 1, 2, 4, 8,
затем 10 секунд без случайного разброса. Подключение библиотеки и проверки
описаны в [документации транспорта](reboop-adoption.md).
Собственный аватар и аватары участников загружаются через тот же транспорт
в режиме `apiBlob`; компонент `ApiImage` отображает локальный `blob:` URL,
отменяет устаревшие запросы и освобождает URL при смене изображения или уходе.
HTTP-ошибки не повторяются; изменяющие данные запросы выполняются один раз,
поскольку сервер мог обработать запрос до потери ответа. Уход со страницы
отменяет чтения, передающие `AbortSignal` из `useData`, включая ожидание повтора.

Это изменение требует обычной сборки и деплоя кабинета. Оно не требует
изменения DNS или настройки API/прокси. Домен API остаётся прежним; выбор IP
контролирует браузер, поэтому бесконечные повторы не гарантируют обход
зависшего маршрута при двух A-записях.

### Проверка запросов кабинета к API

Для случая «страница кабинета открылась, но данные API не загрузились» сохранён
read-only playbook `infra/playbooks/diagnose-platform-api.yml`. Он запускается
на контроллере, без SSH-паролей и доступа к пользовательским сессиям. Проверяет
системный DNS, `/config.js`, CSP, HTTP/TLS и CORS GET/OPTIONS через обычный DNS,
фиксированный origin и фиксированный IP прокси.

```sh
LC_ALL=en_US.UTF-8 LANG=en_US.UTF-8 ansible-playbook \
  -i localhost, infra/playbooks/diagnose-platform-api.yml --tags http

# Дополнительно воспроизвести fetch в изолированном Chromium.
# Требуются зависимости npm проекта и установленный Chromium Playwright.
LC_ALL=en_US.UTF-8 LANG=en_US.UTF-8 ansible-playbook \
  -i localhost, infra/playbooks/diagnose-platform-api.yml --tags http,browser
```

Адреса задаются через `platform_api_origin_ipv4` и `platform_api_proxy_ipv4`.
Браузерные сценарии сравнивают обычный DNS, оба домена через прокси и кабинет
через прокси при API через origin. SNI, HTTPS-проверка и ограничения браузера
сохраняются; профиль пользователя и его cookie не читаются.

26 октября повторно установлено: `/config.js` задаёт
`https://api.mutating.tech/v1`, CSP разрешает этот origin. Через `144.31.78.74`
preflight `/v1/github/status` возвращает 200 с разрешёнными Origin, credentials
и заголовками кабинета. Chromium читает публичный API с кодом 200, защищённые
`/v1/auth/session` и `/v1/github/status` — с ожидаемым 401 в чистой сессии;
CORS-запрета нет. При направлении только API на `85.204.240.76` кабинет по-прежнему
загружается с кодом 200 через VPS, но все три fetch завершаются тайм-аутом.
Прямые curl-запросы к origin также не проходят TLS.

Это воспроизводит сетевой механизм отказа независимо от доступности HTML
кабинета. Для подтверждения причины конкретного запроса авторизованной вкладки
нужны его Status и Remote Address из Network: текст интерфейса «Не удалось
связаться с сервером» используется и для сетевых ошибок, и для HTTP 5xx.
Эта диагностика без cookie не проверяет бизнес-логику авторизованного запроса.
Владелец сообщил, что ошибка в его вкладке исчезла самостоятельно, до изменения
серверов или DNS. Status и Remote Address исходного неудачного запроса не были
зафиксированы. Наблюдение согласуется с выбором рабочего IP либо пересозданием
соединения, но само по себе не доказывает причину того конкретного запроса.
Оба IP сохраняются по ранее принятому решению владельца.

### Перебор адресов браузерами при зависшем TLS

Проверено 26 октября 2026 года на macOS 15.3.1 с текущим VPN. Здесь важно
различать отказ TCP, зависание TLS после успешного TCP и ошибку сертификата:
поддержка Happy Eyeballs для IPv6/IPv4 сама по себе не подтверждает быстрое
переключение между двумя IPv4 после зависания TLS.

Дополнительные read-only сценарии в `diagnose-platform-api.yml`:

```sh
# Доступные браузеры в новых профилях; обычный DNS, с HEv3 и без него.
LC_ALL=en_US.UTF-8 LANG=en_US.UTF-8 ansible-playbook \
  -i localhost, infra/playbooks/diagnose-platform-api.yml --tags matrix

# Google Chrome: временный локальный DoH, оба порядка A-записей и NetLog.
LC_ALL=en_US.UTF-8 LANG=en_US.UTF-8 ansible-playbook \
  -i localhost, infra/playbooks/diagnose-platform-api.yml --tags tls-race
```

Для `matrix` нужны установленные браузеры Playwright; отдельно проверяется
Google Chrome, если он установлен. WebKit Playwright не следует считать
эквивалентом установленного Safari. Для `tls-race` нужны Google Chrome, Node.js,
Playwright и OpenSSL. Сценарий создаёт новые временные профили, локальный
HTTPS DoH-resolver и временный сертификат; доверие по SPKI действует только
для этого resolver в тестовых профилях. Проверка сертификата публичного API
не отключается. Профили и ключ удаляются после проверки; системные DNS, VPN,
действующий профиль браузера и серверная конфигурация не меняются.

Локальный resolver возвращает существующие публичные IP в заданном порядке;
браузер всё равно может дополнительно сортировать адреса. Проверяются actual
TCP attempts в NetLog, наличие HTTP_STREAM_POOL событий для включённого HEv3
и HTTP-ответ. Успешный запрос, сразу выбравший VPS, не доказывает fallback.

Наблюдения:

- Chromium 156.0.8078.4 с обычным DNS получил оба IPv4, начал TCP к
  `85.204.240.76`, успешно установил TCP и не перешёл к VPS за 15 секунд;
  fetch отменён тестовым тайм-аутом.
- Google Chrome 155.0.8059.86 в чистом профиле без принудительного HEv3 также
  зависал на старом адресе при наличии обоих IPv4 в ответе контролируемого DNS.
  Положительный контроль с выбором VPS вернул 200 примерно за 0,8 секунды.
- С `--enable-features=HappyEyeballsV3` код нового connection pool действительно
  использовался, что подтверждено NetLog. В нескольких прогонах запрос зависал
  на старом адресе до 15-секундного тайм-аута. В одном прогоне второй IPv4 был
  запущен примерно через 254 мс и вернул 200 примерно за 1,1 секунды, но первый
  TCP завершился лишь через 278 мс: это гонка на стадии TCP, а не доказательство
  переключения после зависшего TLS. Надёжного решения наблюдаемого сбоя одним
  включением HEv3 на этой сборке не подтверждено.
- Firefox 157.0 Playwright и WebKit 27.2 успешно отвечали через VPS, но в этих
  прогонах выбор нерабочего адреса первым не подтверждён; это не доказательство
  требуемого переключения. Установленный Safari напрямую не проверялся.

Источники состояния реализации: Google описывает
[управление HEv3 флагом/политикой](https://chromeenterprise.google/intl/en_au/policies/happy-eyeballs-v3-enabled/),
а [Chromium](https://raw.githubusercontent.com/chromium/chromium/155.0.8059.86/net/base/features.cc)
содержит выключенный по умолчанию feature flag. В Firefox первоначальное
включение HEv3 в desktop 155 было
[отменено в ветках 155–157](https://bugzilla.mozilla.org/show_bug.cgi?id=2067488);
в [Nightly](https://www.firefox.com/en-US/firefox/158.0a1/releasenotes/) алгоритм
остаётся включённым. Это сведения о включении реализации, а не универсальная
гарантия поведения при любом зависании TLS; конкретный сценарий нужно проверять.

## Общий локальный запуск

Из корня репозитория:

```sh
uv sync --project platform/api --frozen
cp platform/api/.env.example platform/api/.env  # только если собственного .env ещё нет
npm ci
npm run build:web
uv run --project platform/api python deploy/run.py
```

API доступен на `http://127.0.0.1:8000`, кабинет — на
`http://127.0.0.1:8001/`. В `platform/api/.env` укажите
`DASHBOARD_API_URL=http://127.0.0.1:8000/v1`,
`THRONG_PLATFORM_ORIGIN=http://127.0.0.1:8001`,
`THRONG_BROWSER_ORIGINS=["http://127.0.0.1:8001","http://127.0.0.1:5173"]` и
`THRONG_BROWSER_SECURE_COOKIE=false`. Для Vite также используйте
`platform/web/.env.example`. Адрес API должен быть доступен браузеру.

`THRONG_PLATFORM_ORIGIN` задаёт адрес кабинета для перехода из настроек Power Cell.
Укажите origin кабинета в `THRONG_BROWSER_ORIGINS`. Для браузерной сессии
API и кабинет используют один сайт и схему. При общем origin переход работает
по пути `/compute/computers`.

Общая команда применяет миграции, ждёт готовности API, запускает кабинет и
останавливает оба процесса по Ctrl+C/SIGTERM. Неожиданное завершение любого
компонента останавливает второй и возвращает ненулевой код.

## Первичная настройка сервера

Это отдельный административный шаг, который не выполняется обычным CI-деплоем.
Поддерживаются Debian/Ubuntu на amd64/arm64. Используется тот же подход, что в
репозитории `site`: Ansible, nginx, Certbot и SSH-пользователь `user`.

На production nginx совместно обслуживает `mutating.tech` и `pomponchik.org`;
позже можно добавить другие сайты с собственными `server_name`. Обычный деплой
этого репозитория обновляет Hugo, API и кабинет `mutating.tech`. Конфигурации,
сертификаты и содержимое остальных сайтов управляются отдельно. Проверки CI
проверяют домены `mutating.tech`, `www.mutating.tech`, `api.mutating.tech` и
`platform.mutating.tech`.

На уже работающем сервере применяется `infra/playbooks/setup-platform.yml`:
он добавляет виртуальные серверы API и кабинета с точными `server_name`.
Общий `setup-server.yml` предназначен для первоначальной настройки нового
сервера: он также настраивает nginx основного сайта и собирает Hugo-сайт.

Для `setup-site.yml` на контроллере нужны Node.js 24, npm и зависимости после
`npm ci`. Перед синхронизацией playbook собирает UI и готовит отдельный runtime
Hugo в `.runtime/site-runtime` по корневому lockfile командой
`npm ci --omit=dev --ignore-scripts --workspaces=false --no-audit --no-fund`.
Путь можно переопределить параметром `local_runtime_path`. На сервер через
Ansible передаются исходники сайта, UI templates/dist и подготовленный
`node_modules` с production-зависимостями `reboop`; TypeScript, Vite, линтеры
и Node.js для серверной сборки Hugo не требуются. Все шаги подготовки и
синхронизации входят в тег `source_sync`.

14 октября 2026 года `setup-platform.yml` применён к production-серверу:
nginx-маршруты, сертификат обоих поддоменов, systemd-сервис, SQLite-конфигурация
и права пользователя CI проверены. Существующая конфигурация nginx и статическая
страница сохранены. Первый релиз приложений загружает CI после merge в `main`.

1. Создайте DNS-записи `api.mutating.tech` и `platform.mutating.tech`, указывающие
   на сервер. Если есть AAAA-записи, IPv6 тоже должен вести на этот сервер.
2. Откройте входящие 80/443 и SSH-порт. Порты 8000/8001 слушают только loopback.
3. Добавьте платформу к существующему nginx с административного аккаунта после
   переключения DNS:

```sh
LC_ALL=en_US.UTF-8 LANG=en_US.UTF-8 ansible-playbook \
  -i 'SERVER_IP,' infra/playbooks/setup-platform.yml \
  -u root -e ansible_port=22
```

При парольном административном доступе добавьте `--ask-pass`, а если нужны права
sudo — `--ask-become-pass`. Пароли вводите в приглашении Ansible. Пользователя
деплоя можно задать через `-e deploy_user=user`.

Для нового сервера вместо `setup-platform.yml` используйте `setup-server.yml`:
он сначала устанавливает Hugo Extended 0.164.0 и основной сайт.

Playbook платформы устанавливает `uv` версии 0.10.12, nginx, Certbot и инструменты SSH-деплоя,
создаёт отдельного runtime-пользователя `throng`, один systemd unit и дополнительный
nginx-конфиг `/etc/nginx/sites-available/throng`. Сертификат двух поддоменов
хранится отдельно в `/etc/letsencrypt/live/throng-mutating.tech/`; продление
перезагружает nginx после `nginx -t`. Основной конфиг сайта остаётся самостоятельным.

Сервис включается для старта при загрузке машины. Первый CI-деплой создаёт
`/opt/mutating/current` и запускает его. На сервере не требуется Node.js:
интерфейс собирается в GitHub Actions, Python 3.12 устанавливается через `uv`.

Установленные прежде отдельные процессы API/кабинета нужно остановить перед
первым общим запуском, чтобы освободить 8000/8001. Старую SQLite при необходимости
перенесите в `/var/lib/throng/throng.db` при остановленных писателях, включая WAL
либо используя SQLite backup; владельцем должен быть `throng:throng`.

## Включение Power Cell на существующем сервере

Power Cell больше не требует CA, ACME, профиля, relay или открытого порта
`8444`. Нужен только постоянный секрет для идемпотентного завершения
регистрации:

```sh
openssl rand -hex 32
```

Добавьте результат в `/etc/throng/throng.env`:

```dotenv
THRONG_ENROLLMENT_SECRET=<полученное значение>
```

Секрет шифрует только восстановимую копию agent credential до подтверждения
ответа `finish`. Он не является trust anchor и не заменяет пароль или токен.
Храните его вместе с БД в защищённых резервных копиях; при потере незавершённые
повторные `finish` перестанут возвращать тот же credential.

`deploy/activate.sh` при активации релиза создаёт секрет автоматически, если
его ещё нет в `/etc/throng/throng.env`. Кроме того, `deploy/run.py` при старте
без переменной создаёт `.enrollment-secret` рядом с папкой artifacts (в
production — `/var/lib/throng/.enrollment-secret`, права `0600`) и передаёт его
API. Поэтому обычный CI-деплой настраивает регистрацию без ручного изменения
сервера; файл нужно сохранять вместе с базой. Для уже работающего сервера без
нового деплоя добавьте секрет вручную и перезапустите сервис. После изменения
проверьте capabilities:

```sh
curl --fail https://api.mutating.tech/v1/agent-capabilities
```

В `extensions` должны быть `powercell.enrollment.v1` и `powercell.device.v1`;
поля `attestation_required` и `powercell.relay.v1` больше нет. Окончательная
проверка: вход в приложении, регистрация компьютера без профиля macOS, запуск
задачи после привязки к пулу и отвязка.
