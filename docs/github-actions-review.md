Исправлены **19 уникальных причин**:

1. История не принимала допустимый другой регистр UUID, хотя API и редактор
   принимали его. Сравнение и исходящие ссылки используют канонический ID.
2. `cancel` мог пройти старую проверку области OIDC, пересечь редактирование
   ветки/workflows и создать tombstone уже за пределами новой политики.
   Область повторно проверяется в транзакции записи; изменение ресурсов само
   по себе не запрещает корректную отмену.
3. Ограничение старого хранимого `job_key` в 100 символов ошибочно применялось
   к реальным jobs новой схемы. Discovery и выбор YAML принимают длинные
   корректные IDs; legacy storage и его ограничения сохранены.
4. Разные jobs с одинаковым 32-битным префиксом хеша получали одинаковые
   router IDs и YAML anchors. Используется уже существующая 128-битная
   идентичность целиком; объединение двух snippets остаётся однозначным.
5. Общий префикс `powercell_route_` скрывал обычные пользовательские jobs.
   Исключаются только точные формы генерируемых helper IDs, включая старые.
6. Быстро завершившийся подтверждённый job без доставленного события старта
   оставлял привязку в pending. Точное завершение по webhook/REST сохраняет
   доказательство исполнения текущей revision; агрегат workflow этого не делает.
   При поздней доставке сохраняется порядок времён started/finished.
7. Возврат через историю к явной или неявной привязке мог показывать metadata
   другой primary-привязки того же репозитория. Сохранённые metadata теперь
   проверяются по исходному выбранному ID; проверены задержка, 503 и retry.
8. Поздний Save перехватывал фокус после перехода пользователя к другому
   действию. WorkflowSetup проверяет исходную цель фокуса в момент эффекта;
   обычное сохранение по-прежнему раскрывает и фокусирует YAML.
9. Ошибки OAuth refresh в новых endpoints выходили как 500. Вызовы включены
   в существующую границу GitHubError; сохраняются статус/Retry-After,
   policy/history и возможность повтора после окончания ограничения.
10. Смена ветки во время enable/disable теряла успешный ответ команды.
    Форма блокируется на время toggle; при смене URL через историю успех
    перечитывает текущий контекст и сохраняет его URL.
11. Ошибка toggle A показывалась на B и сохранялась после успешного Save B.
    Ошибка хранится с исходным selection и выводится только в нём.
12. Сообщение Save A и фокус его YAML переходили на B после history jump.
    Результат сохранения связан с каноническим целевым selection после Save.
13. При автоматической замене удалённого job после metadata retry новый YAML
    сопровождался сообщением копирования прежнего. Готовый результат copied/
    fallback связан со snippetKey, как и уже имевшаяся защита позднего promise.

14. Ошибка toggle оставалась после успешного retry metadata или Save той же
    канонической привязки. Явное обновление и успешное сохранение завершают
    её жизненный цикл; поздние ответы другой selection по-прежнему изолированы.

15. Независимые parent/child busy допускали Save→Toggle одной revision;
    поздний Save скрывал ошибку нового Disable либо терялся черновик Save.
    BindingForm использует существующее родительское состояние занятости,
    локальное состояние удалено. Обе мутации сериализованы в обе стороны.

16. Новый picker нескольких jobs выдавал конфликтующие router/anchor/default
    instance для legacy-привязки. Явный job_key теперь включает именованную
    идентичность, уже поддержанную runtime; старый no-query YAML проверен
    на точную совместимость. Политика, revision и формат хранения не меняются.


17. Ответ Save/Toggle прежнего пользователя мог смешаться с metadata нового
    аккаунта после реального cross-tab logout/login. Редактор размонтируется
    по actor/repository/installation, существующий mounted guard отвергает ответ.
18. Поздний OAuth-ответ уводил со страницы с черновиком либо с аккаунта нового
    пользователя. Каталог привязан к actor; переход проверяет lifetime страницы.
    Новое действие OAuth по-прежнему работает для обоих путей авторизации.
19. Поздний настоящий 401 от отозванной старой сессии сбрасывал уже подтверждённую
    новую сессию. Публикация подтверждённой сессии продвигает существующий epoch
    API-запросов, включая повторный вход тем же пользователем; актуальный 401
    по-прежнему завершает сессию. Ветка same-user дополнительно проверена в R15.

## Дополнительное прокликивание · 23.10.2026

Повторный проход после предыдущих исправлений. Проверены обычные действия
и сочетания: история → другая привязка → потеря доступа → возврат через историю
браузера; копирование YAML → немедленная смена job/workflow → поздний результат
буфера обмена → повторное копирование.

Подтверждены две причины, сначала получены падающие браузерные регрессии:

1. При возврате к недоступной организационной привязке редактор использовал
   сохранённые metadata личной привязки того же репозитория. Нажатие реально
   отправляло PATCH отключения личной привязки. Теперь явно выбранный ID
   не заменяется другим; metadata без выбранной привязки не показывают её
   форму, YAML или действия. Проверяются отсутствие PATCH до и после 404
   и восстановление через каталог. Сравнение UUID согласовано с API:
   допустимый другой регистр ID не меняет выбранную привязку, в том числе
   до завершения повторной загрузки при возврате через историю.
2. Позднее завершение копирования старого YAML показывало «скопирован» рядом
   с новым YAML либо выделяло новый текст и перехватывало фокус. Обратная связь
   и ручное выделение теперь относятся к исходному workflow/job и исходному
   полю. Проверяются success/failure при смене и job, и workflow, а затем
   успешное копирование текущего текста.

Исправления ограничены редактором и копированием YAML; API и схема БД
не изменялись. Постоянные регрессии с JSDoc:
[actions-click-repeat.spec.ts](../tests/platform/web/e2e/actions-click-repeat.spec.ts).

Финальный общий набор Actions и токенов: **799 passed, 6 skipped, 0 failed**

Подтверждённые исправления:

1. Разбор metadata больше не преобразует допустимые job IDs `on`, `off`,
   `yes`, `no`, `true`, `false`, `null` в boolean/null. Иначе реальные jobs
   исчезали или сливались, а селектор оставался пустым. Исправлена сама стадия
   разбора: `BaseLoader` сохраняет строковые идентификаторы; API по-прежнему
   проверяет структуру и синтаксис job ID. Валидность исходного YAML отдельно
   проверена `actionlint`. HTTP-регрессия сначала упала, затем прошла.
2. Webhooks suspend/delete установки и удаления репозитория теперь записывают
   отключение в существующий журнал ревизий той же транзакцией. Только реальный
   переход enabled → disabled повышает revision. Три HTTP-регрессии сначала
   упали; после исправления проверяют также неизменность прежней записи и
   идемпотентность повторной/новой delivery с тем же событием.
3. Поздний ответ create/edit/toggle после ухода с A на B больше не возвращает
   пользователя в A. Состояние редактора ограничено repo/installation, а
   callback завершённого запроса не публикуется после unmount. Общий `useData`
   не менялся. Реальный browser RED получен для всех трёх mutations, затем
   15 комбинаций этих сценариев прошли во всех пяти браузерных проектах.
4. После develop → main настройка YAML не использует сохранённые metadata
   develop во время загрузки или после ошибки main. Доступ к setup теперь
   требует metadata именно выбранной ветки; черновик формы сохраняется. Browser
   RED показал доступный YAML другой ветки, затем проверяются ожидание, 503 и retry.
   Старый тест немедленной настройки после create выявил слишком широкую первую
   блокировку: вместо запрета любого pending/error метаданные помечены именем
   ветки. Повторная загрузка той же ветки не скрывает уже проверенный YAML.
5. История выбирает первую доступную привязку только при отсутствии явно
   указанного ID. Недоступный ID в сохранённой ссылке больше не подменяется
   историей другого пула. Реальный API подтвердил исчезновение org-привязки
   из списка и 403 на её ревизии после отзыва права; browser RED показал запрос
   ревизий personal-привязки. Исправление ограничено выбором ID и сообщением
   недоступности RU/EN; API-права не менялись.
6. Shared workflow validator больше не ограничивает основу имени 151 символом:
   проверяется существующий полный бюджет пути 250 символов. Валидный workflow
   длиной 182 символа раньше исчезал из discovery и получал reserve403 даже
   при «все workflows». Независимые HTTP/actionlint проверки подтвердили баг;
   regression RED получен для `.yml` и `.yaml` на границе 250. Пути 251 по-прежнему
   отклоняются в обычном поле, списке разрешённых workflows и ключах профилей.
   Схема БД, квоты и проверки опасных символов не менялись.
7. Нормализация `Input` больше не удаляет допустимые Unicode-пробелы с конца
   выбранного ref. Иначе `release\u00a0` сохранялся как другая ветка, а signed
   reserve исходной получал 403. Отключён trim только у `RouteCreate.ref`;
   общая модель и другие поля не менялись. Падающие HTTP-регрессии подтверждают
   проблему с NBSP/EM SPACE; недопустимые ASCII-пробелы теперь отклоняются,
   а не маскируются нормализацией.
8. Имя ветки в metadata query и create/edit допускается до существующего
   полного бюджета ref 250 символов: 239 после `refs/heads/`. Реальные ветки
   201/239 раньше присутствовали в selector, но их выбор/сохранение давали 422.
   Git и HTTP воспроизведения подтвердили это; граница 240 по-прежнему
   отклоняется. Схема БД и проверки запрещённых Git символов сохранены.
9. Frontend больше не обрывает aggregate discovery на 20 секундах. Сквозное
   воспроизведение настоящим `api.ts` к настоящему API с 40 workflows и 550 мс
   на каждый обычный provider request показало клиентский `Network error`
   около 20 секунд и успешный ответ того же серверного запроса около 22 секунд.
   Только каталог и configuration теперь используют отдельный клиентский
   бюджет 90 секунд, согласованный с API proxy. Общий бюджет 20 секунд и
   отмена при уходе сохранены. Browser RED проверяет реальные call sites,
   детерминированный unit RED — завершение aggregate read после 20 секунд;
   обычный запрос по-прежнему истекает, а явная отмена срабатывает сразу.
10. После uninstall/reinstall GitHub App подключение создаётся для текущей
    installation существующим POST. Раньше редактор выбирал архивную привязку:
    PATCH получал 422 из-за неизменяемого installation ID, enable — 404,
    хотя POST успешно создавал новое подключение. Независимое HTTP-воспроизведение,
    затем постоянные API/browser RED подтвердили причину. Автовыбор в metadata
    и редакторе теперь ограничен текущей installation; её отсутствие использует
    default branch репозитория. Старые записи и ревизии сохраняются в истории.
    Явно выбранная старая запись доступна только для чтения и отключения, если
    ещё активна; включение и редактирование чужой installation не предлагаются.
    API identity и существующая защита от дубликатов не ослаблялись.
11. GitHub read-only больше не скрывает локальное отключение CI от владельца
    пула. Настройка и включение по-прежнему требуют GH-admin; отключение требует
    только существующих platform pool permissions. Независимое HTTP-воспроизведение
    подтвердило personal/org owner → 200 и org reader без управления → 403.
    Browser RED подтвердил отсутствие кнопки у обоих владельцев. UI-проверки
    разделены без изменения API; старая браузерная проверка, смешивавшая
    GH read-only с отсутствием прав на личный пул, заменена проверкой
    разрешённого revoke и запрещённых edit/enable. Отрицательные org-проверки
    сохранены; API-регрессии проверяют также аудит и отсутствие provider I/O
    при локальном отключении.
12. Успешный create/edit/enable/disable сразу обновляет достоверное состояние
    выбранной привязки, даже если последующий discovery получает 503. Ответ
    mutation объединяется с прежней расширенной записью, поэтому известный
    `active_runs` не исчезает и повторное включение остаётся заблокированным
    до cleanup. Новая enabled-ревизия ожидает подтверждения workflow, disabled
    отображается отключённой, no-op той же ревизии сохраняет подтверждение.
    Независимый HTTP-прогон подтвердил отсутствие expanded fields в public
    response; browser RED дал четыре ошибки create/edit/disable/enable и один
    успешный no-op. Изменён только merge в callback редактора; общий cache и
    API не менялись. Регрессии проверяют также восстановление discovery.
13. Поздний callback теперь проверяет не только mount/repo/installation,
    но и актуальную выбранную привязку/ветку. Воспроизведён переход editor A →
    history A → archive B → editor B, задержанный PATCH B и переход сразу
    назад к A через меню истории браузера. Компонент переиспользовался, поэтому
    прежняя mount-защита пропускала callback и возвращала пользователя в B.
    Browser RED подтвердил подмену URL; добавлена локальная проверка selection
    без remount по branch, сброса черновиков или изменений общего cache.
14. SQL-пагинация привязок, запусков и ревизий использует существующий общий
    `PaginationOffset`. Значение `2**63` раньше доходило до SQLite и давало 500;
    теперь это validation422. Три HTTP-регрессии прошли RED → GREEN, проверяют
    также допустимую границу `2**63 - 1` и отрицательное значение. Произвольный

## Исправления первой итерации

- Права `execution.read` фильтруются SQL до пагинации привязок.
- Допустимые Job ID сохраняют строковый тип в YAML, включая `null` и `true`.
- Запрашиваемая JIT-метка и `runs_on` совпадают: только уникальная метка.
  Общая `self-hosted` не добавляется: она расширила бы множество jobs,
  которые GitHub может назначить этому runner.
- Отмена/ошибка OAuth проверяет и потребляет state, возвращает в Actions с
  локализованным allowlisted сообщением и сохраняет существующее подключение.
- Неверная подпись webhook, включая произвольные не-ASCII байты, возвращает 401.
- Точки внутри имени репозитория разрешены; traversal запрещён по сегментам пути.
- Подтверждённый отзыв GitHub admin останавливает готовую/выбранную/работающую
  резервацию. Временные сбои не объявляются отзывом прав работающего job.
- После disable свежая выдача JIT запрещена сразу, без ожидания controller tick.
- Polling учитывает GitHub conclusion. Предварительный результат выхода runner
  уточняется поздним webhook или запросом конкретного workflow attempt;
  отмены и timeout при этом не возобновляются.

## Исправления второй итерации

- Disconnect или замена подключения инвалидирует незавершённое создание привязки.
- Приватный одноразовый OAuth claim позволяет disconnect/новому flow отозвать
  уже начавшийся обмен кодом, сохраняя запрет повторного использования state.
- Отсутствующий исторический run не блокирует удаление runner; временная ошибка
  получения результата сохраняет retry, но также не блокирует очистку.
- 404 конкретного ephemeral runner не объявляется отзывом GitHub прав:
  после selection результат остаётся предварительным для позднего completion.
- Сгенерированные routing jobs имеют разные ID для разных привязок одного workflow.
- YAML, UI и API docs требуют upstream needs и approval/concurrency gates до routing;
  выбранный runner по-прежнему ограничен пятью минутами ожидания job.
- Сериализация локального журнала Mac исключает JIT из env, сохраняя полный
  исходный task в памяти для запуска. Это устранение ненужной персистенции,
  а не исправление обхода авторизации на доверенном Mac.

## Исправления третьей итерации

- Активный polling читает конкретный workflow attempt. Новый rerun не подменяет
  результат старого запуска, даже если completion ещё не дошёл до платформы.
- Неверная структура JSON ответа issuer/reserve/commit вызывает настроенный fallback
  и отмену подготовленной резервации; явные terminal failures и чужие метки
  остаются ошибками.
- UI не предлагает организации без `execution.read`: после создания их workflow
  и история иначе были бы недоступны. API policy создания не расширяется.
- Общая проверка управляемых Actions изолятов запрещает ручные mutations через
  обычный execution API, включая command enqueue/cancel, snapshots, renew и destroy.
  Это сохраняет исключительное управление средой CI и границы выдачи JIT.

Swift-регрессия и соседние проверки AgentLifecycle/Journal: 36 прошли; виртуальные
машины в этом прогоне не запускались.

## Исправления четвёртой итерации

- Routing output содержит `run_attempt`. Частичный rerun успешный router обычно
  не повторяет; guard не использует его старую метку. С fallback выбирается hosted
  runner, с `none` workflow останавливается до выделения машины и требует повторить
  routing job с зависимыми jobs или весь workflow.
- Страхующий polling долгих jobs и поздних результатов делит бюджет installation:
  интервал `max(30, 12 × N)` секунд, где N — число незавершённых резерваций её routes.
  Steady polling ограничен 300 проходами/час на installation (до 2700 HTTP при
  текущей стоимости 9 запросов/проход), отдельно от коротких bursts подготовки
  и первой очистки. Ошибки не уменьшают интервал, terminal переход ускоряет cleanup.
  Webhooks и локальные deadlines продолжают обрабатываться сразу.

## Уточнение пятой итерации

OIDC разрешает резервирование конкретному workflow/ref/attempt, однако сам JIT
runner GitHub регистрирует на репозиторий и назначает jobs по меткам. Поэтому
прежнее безоговорочное обещание отсутствия доступа у PR было слишком широким:
bootstrap отправляет PR в fallback, но не является отдельной политикой назначения
GitHub. Уникальная метка не должна считаться секретом.

Контракт и UI теперь явно включают в доверенную границу пула всех авторов jobs
репозитория, включая допущенные PR. Это исправление неверной гарантии и описание
реального ограничения архитектуры, **не** добавление run-bound isolation и не
заявление о воспроизведённой атаке. Предложенный простой job-start hook не добавлен:
его failure не является надёжной защитой от последующих `if: always()` steps.

Основания: [GitHub job metadata](https://docs.github.com/en/rest/actions/workflow-jobs),
[runner authentication/assignment](https://github.com/actions/runner/blob/main/docs/design/auth.md).

## Исправления шестой итерации

- API и UI согласованы с контрактом единственного поддерживаемого Power Cell:
  RAM не меньше 16 MiB, диск не больше 1 TiB. Невыполнимые параметры отклоняются
  до создания изолята, а граничные значения принимаются.
- Бюджет R4 распространён на все terminal reservations: offline Mac не вызывает
  бесконечный GitHub cleanup каждые пять секунд. Сохраняется ранняя контрольная
  проверка после 60-секундного окна поздней регистрации; локальные ресурсы
  по-прежнему удерживаются до подтверждения уничтожения.
- Исправлено устаревшее ожидание независимости snippets после добавления attempt
  guard: тест сохраняет исходные утверждения о непересекающихся router IDs и
  outputs каждой привязки, учитывая новый обязательный guard.

## Исправления седьмой итерации

- Общий переход в running проверяет срок selection, preparation deadline для ready,
  lifetime и состояние изолята. Подписанный поздний start webhook и задержавшийся
  busy poll больше не продлевают уже истёкший ресурс. Нормальный своевременный
  старт из ready/selected по-прежнему поддерживается.
- Ссылки истории содержат `/attempts/{run_attempt}`. Подпись старой попытки
  больше не ведёт в Latest после повторного запуска того же GitHub run ID.

## Исправления восьмой итерации

- Commit и переход в running используют общую проверку VM, команды runner и
  назначенной сессии компьютера в одном SQL-запросе. Известные failure/completion,
  истёкшие lifetime/agent lease и смена сессии больше не публикуют мёртвую метку
  до следующего CI tick; обычный повтор commit остаётся идемпотентным.
- Active reconciliation использует актуальное имя из проверки repository ID.
  Terminal cleanup получает каноническое имя через App metadata по тому же ID,
  сохраняя возможность очистки после OAuth disconnect. Redirect не включается;
  ID и имя ответа валидируются перед credentialed runner-запросами.
- Для новых запусков после rename/transfer нужна новая привязка: OIDC всё ещё
  закреплён за именем/owner/ref исходной политики. Текущая очистка от старого имени
  больше не зависит.

Подтверждённые контракты:

- GitHub [не повторяет неудачные webhook автоматически](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/redelivering-webhooks).
  Контроллер восстанавливает точный результат по
  [jobs исходного attempt](https://docs.github.com/en/rest/actions/workflow-jobs#list-jobs-for-a-workflow-run-attempt),
  включая пагинацию и проверку runner ID/имени. Обязательная очистка runner
  предшествует необязательному запросу результата.
- [Отзыв пользовательской авторизации](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app)
  приходит обязательным событием `github_app_authorization`; теперь оно прекращает
  локальные полномочия, включая уже начатые OAuth exchange/refresh.
- [Rate limit](https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api#rate-limit-errors)
  возвращается как 403 или 429. Общая задержка следует Retry-After/reset и не
  обходится ротацией user/installation token; обычный permission 403 обрабатывается
  отдельно. Отставший успешный ответ не снимает более новое ограничение.
- Workflow [наследует рабочий каталог](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#defaultsrunworking-directory).
  Routing использует существующий `runner.temp`, поэтому может стартовать до
  checkout в монорепозитории с `defaults.run.working-directory`.

ответа и нового rate limit: 1 failed / 1 passed до исправления. Тесты результата
