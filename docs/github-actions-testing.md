# Проверки интеграции GitHub Actions

**Актуальная схема с 19 октября 2026:** только Power Cells. Нет свободного Mac —
немедленный отказ без VM/JIT; ошибки API/подготовки завершают routing и весь workflow
с failure, основной job пропускается. Политика fallback и её UI удалены. Routing
и queue guard остаются hosted: нужны hosted минуты. Требуйте routing, workload
и queue guard checks в защите ветки.
Существующий YAML необходимо заменить новым примером целиком. Упоминания прежней
схемы под датированными заголовками ниже — история проверок. Текущие
контракты не содержат отдельного `/commit`: выбор фиксирует сам `reserve`.

## Браузерная приёмка и настоящий GitHub · 20.10.2026

В авторизованном браузере проверены OAuth, отключение/подключение аккаунта,
выбор установки App и владельца, личный/организационный пул, выбор/сброс Mac,
создание привязок, применение YAML через редактор GitHub, dispatch, история,
отключение, refresh и мобильный интерфейс на русском/английском.

Исправлены два недостатка: после DELETE 204 и следующего GET 503 интерфейс
сохраняет подтверждённое отключение; перед отключением GitHub объясняется отзыв
всех созданных пользователем привязок и необходимость обновить YAML после подключения.
Оба сценария сначала воспроизведены тестами, первый — также на настоящем API с
контролируемым сбоем только чтения. Полный набор: **325 passed** в Chromium,
Firefox, WebKit и мобильных вариантах; после дополнения — **15 passed** целевых

## Сквозное ревью пяти областей · 19.10.2026

Пять независимых ревьюеров проверили App/OAuth/OIDC/HTTP, резервирование,
controller/webhooks, workflow/UI и native runner. Подтверждённые дефекты
сначала воспроизведены тестами. Новые API-тесты используют настоящие TCP HTTP,
SQLite, подписанные OIDC/webhooks, транзакционные барьеры и перезапуск хранилища;
внешний GitHub подменяется локальным HTTP-сервисом с управляемыми сбоями.

Исправления:

- Сроки reserve, cancel, webhook и controller считаются после получения write lock.
  Отмена выдаёт полный срок доставки cancel/destroy даже после задержки БД и
  временной потери связи с агентом (component + HTTP e2e; 3 мутации).
  Истёкший controller claim не обращается к GitHub; остаток lease ограничивает
  запросы, запоздавший worker не освобождает claim своего преемника.
- GitHub HTTP имеет общий deadline, включая медленную выдачу тела. Rate limit
  сохраняется по заголовкам даже при оборванном теле. Refresh учитывает ожидание
  БД/commit; upstream отказ возвращает корректный HTTP статус без секретов.
- OIDC повторно проверяет фактическое время после ожидания JWKS и lock.
- Новый read-only `/watch` привязан к route/run/attempt/instance, не выделяет
  ресурсы и не продлевает lease. Согласованный snapshot исключает ложный timeout
  при одновременном webhook. Миграция `0013` сохраняет подтверждённый старт,
  чтобы выход runner и временный отказ outcome API не отменяли выполненный job.
- Новый пример YAML использует workload и hosted queue guard в одной матрице.
  Ошибка guard вызывает нативный fail-fast только этой матрицы/attempt. Все
  исходные CI steps должны иметь workload condition; инструкция RU/EN и
  браузерный тест проверяют это. Требуйте routing, workload и guard checks.

В ещё не выпущенной native network-recovery ветке отдельно исправлены запись
GitHub JIT на диск и ошибочная финализация при временном отказе result receipt.
62 Swift-теста и 8 мутаций прошли; installed build 24 не заменялся, отдельная
native/API экспериментальная функциональность не включается в этот API-релиз.

Проверка удаления fallback: **535** GitHub/API тестов, **86** регрессий общего
execution/авторизации/планировщика/миграций и **135** браузерных сценариев прошли.

Моки покрывают отсутствие/занятость/несовместимость Mac, конкурирующее выделение,
ошибки образа/сети/GitHub/OIDC, потерю reserve, отмены, повторные attempts
и очистку. Миграция проверяет сохранность истории и незавершённой очистки.

реализации исправляется без ослабления утверждений теста.

React и HTTP-клиент настоящие. Управляемый
[HTTP peer](../tests/platform/web/e2e/actions-peer.ts) заменяет ответы GitHub/CI
эндпоинтов и списков пулов; он сохраняет запросы и позволяет задерживать ответы
или возвращать конкретные ошибки. Эти проверки не доказывают работу API:
для неё существует отдельный сквозной набор ниже.

Проверяются:

- подключение, повторная авторизация и установка App; безопасный redirect;
  отмена OAuth, ошибка провайдера и неизвестный callback result без отражения его текста;
- ошибки статуса, авторизации, отключения и загрузки списков, последующий retry;
- пустые страницы пагинации, смена владельца, suspended installations,
  публичные и приватные репозитории, отсутствие прав администратора;
- личный и корпоративный пул, разрешения управления ресурсами, запуска и чтения,
  фильтрация компьютеров по runtime, сброс выбора при смене пула;
- CPU/RAM/disk и преобразование единиц, предел диска агента 1 TiB, параллельность, срок подготовки;
- браузерная валидация, сохранение формы после отказа API, защита от двойного submit;
- отключение привязки, повторная загрузка workflow и истории после ошибки;
- статусы и причины отказа, ссылка на конкретный attempt, неизвестные причины;
- поздние ответы при переключении привязки, английский язык и узкий экран;
- читаемые действия карточек при длинных названиях на ширинах 320–1440 px;
  переход к выбранным деталям и ошибкам с клавиатурным фокусом ниже sticky header;
- реальные GitHub conclusions, включая success/failure/cancelled/timeout,
  default branch каждого репозитория и явное переопределение ref;
- локальная проверка предельных ресурсов платформы, зарезервированного Job ID
  и некорректных refs; retry загрузки пулов/компьютеров без преждевременного submit;
- явная загрузка истории, пустой пул и сброс конкретных компьютеров без modifier keys;
- обновление репозиториев без сброса формы/открытой истории и повторных запросов,
  устойчивые ошибки refresh и их восстановление; понятная причина suspended installation;
- запрет создания по устаревшему списку репозиториев до успешной проверки прав;
- Git-валидные компоненты ветки: запрет `.hidden`, `.lock`, завершающих точки и слеша;
- права на отключение корпоративной привязки при доступной для чтения истории;
- сохранённые диск, ожидание, компьютеры, параллельность в деталях;

## Сквозная цепочка с моками внешних участников

[23 сценария](../tests/platform/api/e2e/powercell/test_ci_chain.py) используют
[стенд](../tests/platform/api/e2e/powercell/ci_chain_peer.py), который связывает:

1. OAuth, проверку одноразового state, просмотр установок и репозиториев.
2. Создание привязки через API и разбор сгенерированного workflow YAML-парсером:
   события, permissions, env, routing job, зависимость и динамический runs-on.
3. Извлечение **именно встроенного в этот workflow Python-кода** из разобранного
   YAML и его исполнение.
4. Получение подписанного RSA OIDC-токена у тестового HTTP issuer.
5. Настоящие HTTP reserve/poll/cancel запросы bootstrap к API.
6. SQLite, общий планировщик и реальный учёт занятых ресурсов.
7. Настоящее ACME/device enrollment тестового агента, подписанные heartbeat,
   claim/started/complete и сверку сессии при переподключении.
8. Создание изолята с образом `actions`, ресурсами и сетью; регистрацию JIT,
   выдачу секрета назначенному агенту и подтверждение готовности runner.
9. Выбор точной метки runner, старт job, HMAC webhook и историю результата.
10. Отмену команд, destroy, удаление GitHub runner и подтверждённое освобождение
    резервов CPU/RAM/disk. Для каждого сценария проверяется отсутствие секретов
    в логах, YAML, outputs и сохранённых payload заданий.

Bootstrap сохраняет настоящий `urllib` request/JSON/error handling. Тестовый
сетевой адаптер направляет адрес issuer и публичный адрес платформы на loopback
после штатной проверки URL. Внутренние функции авторизации, резервирования,
планировщика, сериализации и контроллера не заменяются моками.

| Сценарий | Что фиксируется |
| --- | --- |
| Job success / failure / cancelled | Правильный результат, история, одна регистрация и полная очистка |
| Нет Mac | Немедленный failure, без изолята/JIT/output; повтор возвращает тот же отказ |
| Ошибка образа / offline runner / отказ GitHub | Failure routing, отсутствие позднего назначения, очистка |
| Потерян ответ reserve | Cancel после фактического изменения БД, отсутствие двух выбранных runners |
| API недоступен до reserve | Failure и cancellation tombstone без изолята |
| Ошибка связи / некорректный ответ | Явная ошибка routing job, отсутствие `runs_on` output |
| Отмена workflow при подготовке | Нет runner output, остановка подготовки и освобождение ресурсов |
| Потерян start webhook | Восстановление running через GitHub polling, затем timeout и очистка |
| Повтор workflow | Новый attempt, новая метка и JIT, сохранение истории |
| Чужой подписанный OIDC | Никаких ресурсов или регистраций в чужой привязке |
| Новый экземпляр API | Новые HTTP app, DB pool, crypto client и JWKS cache используют сохранённое состояние |
| Браузерная cookie-сессия | Полная цепочка с CSRF, без bearer платформы; чужой Origin отклоняется |
| Корпоративный пул | Передача Mac отзывает прежние credentials; новая регистрация, выбор конкретного Mac и организация изолята проверяются через API |
| Потерян Mac | Резервы сохраняются до подтверждённого `clean_start`; job не воспроизводится |
| Retry bootstrap / второй matrix instance | Идемпотентность и соблюдение общей квоты параллельности |
| Disconnect после выбора | Очистка работает через App после удаления пользовательского OAuth |
| GitHub запрещает удаление runner | Cleanup не объявляется завершённым; последующий retry удаляет регистрацию |
| Повтор и нарушение порядка webhook | Завершённый attempt не возобновляется; cleanup выполняется один раз |

GitHub API изображает stateful HTTP transport, а тестовый агент изображает
выполнение VM RPC и runner-процесса. Бинарник официального runner, реальная VM,
checkout, произвольные CI steps и загрузка артефактов в GitHub этим набором не
исполняются. Их проверка остаётся отдельной живой приёмкой. Стенд проверяет весь
платформенный протокол между этими границами; GitHub billing для него не нужен.

## Дополнительное ревью отказов, 20.10.2026

Пять независимых ревьюеров проверили авторизацию, создание резервации,
контроллер, workflow и нативный транспорт. Три подтверждённых дефекта платформы
сначала воспроизведены основным агентом на прежней реализации:

- Ошибка записи initial-state после частичной записи оставляла файл без записи
  в БД и учёта квоты. Запись перенесена внутрь существующего блока очистки.
  Компонентный и HTTP-тесты дважды записывают настоящие 512 байт перед ENOSPC;
  после каждого отказа проверяют файлы и БД. Отдельный дочерний процесс с
  `RLIMIT_FSIZE` подтвердил такое поведение настоящей файловой системы.
- Оборванный HTTP-ответ с `Content-Length` мог ошибочно считаться окончательным
  JSON-ответом: `HTTPResponse.read(amt)` сам не проверяет недостающие байты.
  Bootstrap проверяет оставшуюся длину после проверки предела размера.
  Одиннадцать тестов настоящего HTTP и две сквозные проверки guard воспроизводят
  обрыв, повтор и сохранение здорового запуска. Тестовый peer теперь передаёт
  настоящий `HTTPResponse`, без предварительного полного чтения тела.
- Если REST GitHub временно возвращал пустой список или ещё queued job,
  контроллер мог навсегда подменить результат уже выполнявшейся job итогом
  всего workflow. Теперь точный результат уточняется независимо от освобождения
  VM, удаления runner и удаления credentials. Семь новых сквозных сценариев

без возврата на прежний URL. Ошибка другой привязки, полученная до или после
перехода через историю, не показывается в текущем редакторе и после его
успешного сохранения. Сообщение Save и фокус YAML также принадлежат сохранённому
контексту. При автоматической замене удалённой job после metadata retry прежние
copied/manual-copy сообщения не относятся к новому YAML, а его копирование
работает отдельно. Ошибка текущей привязки завершается после успешного retry
или Save на том же каноническом URL. Docstrings/JSDoc описывают причину каждого
дефекта. Общая занятость проверяется в обе стороны: pending Toggle блокирует
редактирование, pending Save блокирует Toggle, а после завершения следующая
команда использует свежую revision и сохраняет обе последовательные правки.

uv run --project platform/api pytest -c platform/api/pyproject.toml \

npm run build:web
npm run test:e2e --workspace platform/web -- e2e/actions-edge-cases.spec.ts

`actions-session-edge.spec.ts` использует настоящие login/logout, cookies и
`users/me`: поздние Save, Toggle, OAuth и реальный 401 старой сессии не должны
перезаписывать новый аккаунт или завершать новую сессию. Проверяется и повторный
вход тем же пользователем: подтверждение новой сессии делает прежний 401
неактуальным независимо от совпадения user ID. После этого текущий Save работает;
обработка настоящего текущего 401 отдельно проверяется в `api-session.test.ts`.
`actions-oauth-edge.spec.ts` проверяет оба OAuth-действия при уходе в редактор:
поздний ответ не уводит со страницы с черновиком, новое действие авторизации
по-прежнему переходит на правильный GitHub URL.

`test_actions_refactoring.py` закрепляет границы общих API-функций до их
объединения: одинаковую видимость в списке, каталоге и metadata, личные и
организационные права, фильтрацию до SQL-пагинации при равных timestamps;
create/edit × личный/организационный пул × default/profile × корректный,
чужой, отсутствующий и неподдерживаемый компьютер. Отказы не меняют настройки,
историю и артефакты. Reserve/cancel изолированы по route/run/attempt/instance,
сохраняют соседние резервации и идемпотентность повторов.
`test_ci_workflow_profiles.py` проверяет генератор YAML для старой и новой
схемы: выбранные workflow/job, длинные job IDs, точные instances, буквальные
фильтры веток и эффективные таймауты без изменения объекта политики. Вместе
это 65 проверок, пройденных до и после упрощения.
