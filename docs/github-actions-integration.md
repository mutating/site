# GitHub Actions через Power Cells

Статус на 16 октября 2026 года: согласованный проект интеграции. Загрузка
официального образа runner, псевдонимы `ubuntu` / `actions` и маршрутизация
образов уже реализованы. GitHub App, вкладка Actions, резервирование для CI и
описанный ниже workflow ещё не реализованы. Проверка настоящего workflow
в GitHub остаётся отдельным критерием готовности.

## Сценарий пользователя

1. Пользователь платформы привязывает GitHub-аккаунт через авторизацию GitHub App.
2. Владелец GitHub-аккаунта или организации устанавливает App и выбирает доступные
   репозитории. Авторизация пользователя и установка App — разные части связи.
3. Во вкладке Actions пользователь выбирает репозиторий, workflow и job, личный
   пул или пул организации, при необходимости конкретные компьютеры.
4. Для job задаются CPU, память, диск, предел ожидания Power Cell, fallback runner
   и предел параллельных запусков. CPU задаются в логических ядрах одного
   исполнителя, а не в количестве компьютеров. Один job не складывает ресурсы
   нескольких Mac.
5. Интерфейс выдаёт изменение workflow: вспомогательный job выбора исполнителя,
   зависимость `needs` и динамический `runs-on` основного job.
6. При запуске workflow платформа пытается подготовить одноразовый runner в
   подходящем Power Cell. Если подготовка не уложилась в срок, основной job
   получает заранее выбранный GitHub-hosted fallback.
7. Основной job, логи, результаты и артефакты остаются в GitHub Actions. Кабинет
   показывает выбранный backend, компьютер, выделенные ресурсы, причину fallback
   и ссылку на запуск GitHub.

Организации платформы и GitHub не обязаны совпадать. Право управлять GitHub
репозиторием само по себе не даёт права расходовать пул организации платформы.
Привязка проверяет обе стороны, а отзыв прав останавливает новые назначения.

## GitHub App и доступы

Первая версия использует runners, зарегистрированные для конкретного
репозитория. Это позволяет ограничить установку App выбранными репозиториями.

| Repository permission | Уровень | Назначение |
| --- | --- | --- |
| Metadata | Read | Идентификаторы и метаданные репозиториев |
| Contents | Read | Чтение workflow для настройки привязки |
| Actions | Read | Workflows, jobs и статусы запусков |
| Administration | Write | Регистрация JIT runners, проверка состояния и удаление |

`Administration: write` требуется GitHub API для repository JIT runners.
Права `Contents: write` и `Workflows: write` не входят в базовую установку:
пользователь применяет сгенерированное изменение workflow сам или через отдельный
доступ разработчика к тестовому репозиторию. Доступ для тестовых push/dispatch
не следует путать с постоянными разрешениями App.

Для runners уровня GitHub organization существует отдельное разрешение
`Self-hosted runners: write`. В первой версии оно не нужно.

App получает события `workflow_job`, `workflow_run` и события изменений установки
и списка доступных репозиториев. Webhook подпись и идентификатор доставки
проверяются; повторы и нарушение порядка событий не должны повторно назначать
ресурсы или менять уже завершённый результат.

Планируемые адреса для production; до реализации обработчиков они не работают:

| Назначение | Адрес |
| --- | --- |
| Homepage | `https://platform.mutating.tech/` |
| OAuth callback | `https://api.mutating.tech/v1/github/oauth/callback` |
| Installation setup | `https://api.mutating.tech/v1/github/installations/callback` |
| Webhook | `https://api.mutating.tech/v1/github/webhook` |

Создание App и installation выполняет владелец GitHub-аккаунта/организации.
Настройка сервера потребует App ID, Client ID, Client Secret, private key,
webhook secret и ключ шифрования сохранённых credentials. Секретные значения
хранятся в конфигурации сервера; они не входят в репозиторий и workflow.

## Выбор исполнителя

Вспомогательный job выполняется на GitHub-hosted runner. Он также использует
минуты/лимиты GitHub и не обеспечивает независимость от доступности GitHub.
Он обращается к платформе с короткоживущим GitHub OIDC token. Долгоживущий
персональный токен платформы в репозитории для этого не нужен.

Проверяются подпись, issuer, audience, срок токена, GitHub repository/owner ID,
разрешённый workflow/ref, событие, run ID и attempt. Переданные клиентом имя
репозитория, владелец пула или route ID не заменяют эти проверки. Авторизация
OAuth связывается с существующей сессией платформы одноразовым `state`.

Проверка наличия свободной машины заменяется атомарной резервацией. Обработка
идёт через существующий учёт ресурсов, чтобы обычные изоляты и CI не могли
одновременно занять один слот. Резервация имеет срок жизни и уникальную метку
runner. Матрица jobs требует отдельной резервации для каждого экземпляра job;
повтор workflow использует новый attempt. Транспортный повтор запроса не создаёт
нового runner и возвращает то же решение.

Контроллер создаёт изолят с `image: "actions"` и зафиксированными ресурсами,
получает JIT-конфигурацию GitHub, запускает официальный runner и проверяет его
готовность. В основном job используется метка этого runner. Общие метки пула
недостаточны для соблюдения индивидуальных ресурсных требований job.

JIT-конфигурация и токены не должны попадать в общедоступные ответы, обычные
описания команд, диагностические логи или сохраняемые шаблоны. При реализации
нужно проверить существующее хранение command/env и добавить защищённую передачу
временных runner credentials там, где это требуется.

Загрузка образа, создание VM, регистрация и готовность runner входят в общий
предел подготовки. Решение о fallback фиксируется до выдачи результата
вспомогательного job. Поздно завершившийся runner после выбора fallback
останавливается, а его резервация и регистрация удаляются. Очистка повторяется
после рестарта сервера и подтверждается агентом перед освобождением занятого
диска и памяти.

После начала основного job автоматический перенос его выполнения на другой
backend в первую версию не входит. Потеря Mac или ошибка тестов завершают attempt
по отдельным правилам; повтор деплоя/публикации не должен происходить неявно.
Даже готовый runner может исчезнуть между решением и получением задания:
механизм начального выбора не гарантирует fallback для такого случая.

При недоступности API вспомогательный job выбирает настроенный fallback за
ограниченное время. Ошибки конфигурации и авторизации должны быть видны
пользователю; fallback не считается успешной привязкой к Power Cells.

## Совместимость и границы

Рабочая среда на Mac сейчас — Linux ARM64 внутри VM. macOS/Xcode jobs требуют
другого исполнителя. Официальный runner image не равен полному набору ПО
GitHub-hosted runners; workflow устанавливает необходимые инструменты явно.
Текущие изоляты не поддерживают Docker service/container actions и повышение
привилегий. Подходящий Power Cell должен удовлетворять требованиям среды,
сети и ресурсов, а не только быть online.

GitHub предоставляет Ubuntu ARM64 runners. Выбор fallback проверяет архитектуру
и заявленные минимумы ресурсов. Если стандартный runner меньше необходимого,
нельзя обещать выполнение с теми же минимумами: нужен подходящий larger runner,
другой подключённый провайдер либо явный отказ от fallback для этой привязки.
Лимиты и тарификация GitHub продолжают действовать и могут не позволить запуск.

Начальный набор политик: push и pull requests из разрешённого репозитория;
pull requests из fork по умолчанию направляются на GitHub-hosted runners.
Допуск к корпоративным Power Cells задаётся отдельно от доступа к репозиторию.

Другие пулы Actions runners могут подключаться как дополнительные провайдеры
исполнения. Отдельный CI-движок требует адаптера запуска, статуса, отмены,
логов и артефактов. Он не является совместимым с произвольным Actions workflow
только благодаря наличию API запуска команд.

## Что требуется для живой проверки

1. Отдельный тестовый репозиторий, предпочтительно private, с включёнными Actions
   и доступными GitHub-hosted минутами. Нужен доступ из рабочего окружения для
   изменения workflow, push, dispatch, чтения статусов, логов и артефактов.
2. Владелец GitHub App — личный аккаунт или организация. После реализации
   callback/webhook App устанавливается только в тестовый репозиторий.
3. Развёрнутый тестируемый API на HTTPS-адресе, доступном GitHub и Mac,
   возможность применить миграции и установить серверные credentials App.
   Это может быть отдельный стенд: production для первых проверок не обязателен.
4. Один Apple Silicon Mac с обновлённым агентом, включённой сетью и достаточными
   ресурсами. Он должен быть привязан к тому же экземпляру платформы.
5. Аккаунт платформы и тестовая организация для проверки личного пула,
   организационного пула, разрешений и их отзыва.

Эти внешние условия нужны для проверки настоящего GitHub job. Подготовка
серверной интеграции, UI, вспомогательного action, миграций и автоматических
тестов может идти до получения доступов.

Пошаговая инструкция подготовки тестового репозитория, GitHub App и credentials
на текущем Mac — в [настройке для разработки](github-actions-dev-setup.md).

## Критерии готовности

| Сценарий | Ожидаемый результат |
| --- | --- |
| Есть подходящий Power Cell | Настоящий GitHub job выполнен внутри изолята; в GitHub видны его runner и логи |
| Нет свободных машин, они offline или квот недостаточно | Ограниченное ожидание, затем GitHub-hosted job с понятной причиной выбора |
| API недоступен или VM/runner не успели подготовиться | Fallback в заданный срок; поздний runner не получает задания |
| Параллельные jobs и matrix | Отдельные резервации без превышения общей квоты |
| Повтор запроса и повтор workflow | Запрос идемпотентен; новый attempt не наследует старую регистрацию |
| Отмена workflow, удаление привязки или отзыв установки | Остановка/удаление runner, очистка изолята и освобождение ресурсов |
| Перезапуск API или агента в ходе подготовки | Восстановление состояния и подтверждённая очистка без двойного запуска |
| Отзыв прав в организации платформы или GitHub | Новые назначения прекращаются |
| Ошибка теста или потеря Mac после старта | Видимый результат attempt; отсутствует неявный повтор публикации/деплоя |
| Подмена OIDC claims, webhook подписи или повтор доставки | Запрос отвергнут; ресурсы другого владельца недоступны |
| Логи, артефакты и завершение обоих backend | Результаты доступны в GitHub; платформа показывает фактического исполнителя |
