Аннотации типов Python описывают больше, чем можно напрямую проверить через `isinstance()`, но многим компонентам во время выполнения нужен лишь дешёвый ответ «совместимо или нет», а не рекурсивная валидация, преобразование значений, декораторы или целая система схем.

[simtypes](https://github.com/mutating/simtypes) — Python-библиотека без зависимостей для этого узкого вопроса. Её [первый релиз](https://github.com/mutating/simtypes/releases/tag/0.0.1) предоставляет один предикат, который понимает обычные классы, объединения, optional-типы, `Any`, `None` и наблюдаемый внешний тип параметризованных аннотаций.

## Предикат, а не система типов

Версия 0.0.1 экспортирует `check(type, value) -> bool`. В историческом API сначала передаётся тип:

```python
from simtypes import check

check(int, 42)                    # True
check(int | None, None)           # True
check(list[str], [1, 2, 3])       # True
```

Последний результат намеренный. В этом релизе `list[str]` задаёт вопрос «это список?», но не перебирает элементы и не проверяет, что каждый из них — строка. Обычные классы проходят через `isinstance`, а для `Any`, `None`, объединений, optional-аннотаций и внешнего runtime-типа параметризованных аннотаций существуют небольшие явные правила.

Поэтому стоимость проверки коллекции предсказуема и не растёт с её длиной. Но по той же причине simtypes 0.0.1 не подходит для проверки недоверенных вложенных данных и не доказывает соответствие всей статической аннотации. Пакет сознательно не берёт на себя такое обещание.

В итоге получается небольшой checker без runtime-зависимостей, декораторов, import hooks, приведения значений и компилятора схем. Вызывающий код получает булево значение и сам решает, что с ним делать.

## Альтернативы мощнее

В Python уже есть отличные runtime-checker-ы. [Typeguard](https://typeguard.readthedocs.io/en/latest/) и [Beartype](https://beartype.readthedocs.io/) понимают гораздо больше аннотаций и умеют автоматически обеспечивать контракты. [Runtype](https://runtype.readthedocs.io/en/stable/validation.html) рекурсивно проверяет коллекции, а [Pydantic TypeAdapter](https://docs.pydantic.dev/latest/concepts/type_adapter/) ещё и преобразует и сериализует структурированные данные.

Когда нужна такая семантика, эти инструменты лучше. simtypes не выигрывает полнотой `typing` и не является первым булевым checker-ом. Его преимущество — меньший контракт: никакого автоматического enforcement, никаких преобразований значения и гарантированный отказ от просмотра элементов коллекции в базовом режиме.

Для одного места вызова лучшим решением всё ещё может оказаться локальная функция поверх `isinstance()` и `typing.get_origin()`. Пакет становится полезен, когда одна и та же скромная политика должна тестироваться, версионироваться и использоваться несколькими библиотеками.

## Специализация

simtypes задуман как строительный блок для runtime-инфраструктуры, которой нужно дешёвое решение о совместимости, а не собственный фреймворк валидации. Диспетчеризация, регистрация плагинов, поля конфигурации и другие механизмы могут полагаться на единый ответ, не подтягивая большую систему enforcement.

Таково и его неброское место в более крупном наборе инструментов: поддерживать границы между компонентами, оставаясь слишком маленьким, чтобы диктовать их архитектуру.

## Что дальше

В планах — явный строгий режим проверки содержимого коллекций, несколько полезных специальных числовых типов и более естественный порядок аргументов `check(value, type)`. Затем появится десериализация строк, включая даты и время, а позже — парный сериализатор для контролируемого round trip поддерживаемых значений.

Эти возможности должны остаться дополнительными слоями вокруг того же принципа. simtypes не будет воспроизводить все правила, о которых способен рассуждать статический анализатор. Его задача — ответить на наблюдаемый runtime-вопрос и честно обозначить то, что мы намеренно игнорируем.
