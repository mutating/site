Приложения редко получают настройки из одного места: значения по умолчанию, аргументы конструктора, переменные окружения, файлы и секреты конкурируют за итоговое значение. В долгоживущей Python-программе настройки также могут меняться после запуска. Если загрузка и последующее присваивание подчиняются разным правилам, в работающее приложение могут попасть невалидные или конфликтующие значения, callbacks увидят несогласованное состояние, а диагностика раскроет секреты.

[Pydantic Settings](https://docs.pydantic.dev/latest/concepts/pydantic_settings/), [Dynaconf](https://www.dynaconf.com/) и [Hydra](https://hydra.cc/docs/intro/) предоставляют развитые средства загрузки, валидации, слоёв и переопределений. Их основные модели не объединяют в одном объекте выбор источников для отдельных полей, согласованные изменяемые присваивания, явные конфликты, callbacks и безопасные для секретов ошибки. Приложению, которому эти гарантии нужны после запуска, иначе приходится строить дополнительный жизненный цикл конфигурации поверх загрузчика.

[skelet](https://github.com/mutating/skelet) — конфигурационная Python-библиотека для настроек, которые могут меняться после загрузки. Она объединяет типизированные поля, упорядоченные источники, контролируемое присваивание, блокировки отдельных полей, явные конфликты и безопасные для секретов ошибки. [Релиз](https://github.com/mutating/skelet/releases/tag/0.0.1) доступен на GitHub.

## Валидируемые изменения во время выполнения

Класс `Storage` объявляет типизированные поля. Значения могут приходить из аргументов конструктора, переменных окружения, TOML — включая `pyproject.toml`, — JSON, YAML или памяти. Источники упорядочены, и выигрывает первый, в котором найдено значение. Отдельные поля могут заменить или расширить этот общий порядок.

```python
from skelet import EnvSource, Field, Storage, TOMLSource

class Settings(
    Storage,
    sources=[
        EnvSource(prefix="my_app_"),
        TOMLSource("pyproject.toml", table="tool.my_app"),
    ],
):
    retries: int = Field(3, validation=lambda value: value >= 0)
    api_token: str = Field("", secret=True)

settings = Settings()
settings.retries = 5       # После загрузки действуют те же проверки.
settings.retries = -1      # Поднимает ValueError; сохранённым остаётся 5.
```

Здесь переменные окружения приоритетнее TOML-таблицы, а та — значений полей по умолчанию. Последующее присваивание всё равно проходит проверки типа и значения.

До сохранения skelet умеет преобразовать значение, проверить его runtime-тип и запустить пользовательские валидаторы. Поле может быть read-only, содержать документацию, иметь алиасы или явно конфликтовать с другими полями. После успешного изменения callback получает старое значение, новое значение и объект хранилища.

Эти правила продолжают действовать и при последующих изменениях. Записи одного поля сериализуются, а конфликтующие поля координируются, чтобы их связь проверялась согласованно. Это не транзакционная база данных: изменение элемента внутри сохранённого объекта обходит поле, а ошибка callback не откатывает присваивание. Обычное присваивание полю при этом проходит определённую последовательность валидации и уведомлений.

## Работа с секретными значениями

`secret=True` скрывает поле в представлении хранилища и в стандартных сообщениях об ошибках skelet. Он не шифрует объект, не стирает его из памяти, не вводит контроль доступа и не получает значения из vault. Код приложения всё ещё может прочитать и раскрыть исходное значение.

Это важное различие: безопасная диагностика секретов и управление секретами — разные задачи. skelet решает первую.

## Сравнение с развитыми инструментами конфигурации

Эти проекты предлагают более развитые экосистемы загрузки: вложенные модели, CLI-ввод, удалённые источники секретов, иерархическую композицию и reload. [Typed Settings](https://typed-settings.readthedocs.io/en/latest/) — ещё один вариант с компонуемыми loaders и сгенерированными CLI. Более узкая специализация skelet — жизненный цикл изменяемых полей после загрузки: согласованные записи, явные конфликты и callbacks при присваивании.

Пакет предназначен для библиотек, сервисов и долгоживущих инструментов, чьи настройки одновременно загружаются из нескольких мест и законно меняются после создания объекта. Если достаточно неизменяемого снимка при старте, более узкий loader может быть лучшим выбором.

## Что дальше

Проект будет упрощать объявление и расширение типизированной конфигурации для большего числа источников и типов значений. Встроенные и сторонние источники постепенно перейдут к общей модели расширения, чтобы сохранить компактное ядро хранилища и поддержать единый конфигурационный слой для связанных инструментов.
