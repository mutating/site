Python-инструменты используют много несовместимых форм машиночитаемых комментариев: `noqa`, `type: ignore`, `fmt: off`, `pragma: no cover` и другие. Для каждой формы нужны собственный парсер, правила экранирования и способ сосуществования с обычным текстом или другой директивой. В результате похожие команды ведут себя по-разному, инструменты могут неверно читать чужие комментарии, а каждый новый анализатор повторяет ту же работу по разбору.

Декораторы, `typing.Annotated` и конфигурация проекта дают структурированные метаданные в других областях, но не позволяют разместить любую инструкцию непосредственно рядом с отдельным выражением исходного кода, не меняя сам код. Inline-директивам нужен общий синтаксис, смысл которого по-прежнему определяет конкретный инструмент.

[metacode](https://github.com/mutating/metacode) — Python-библиотека для разбора машиночитаемых инструкций в комментариях с помощью одной компактной грамматики. Она задаёт общую форму `key: command[arguments]`, поверх которой инструменты для работы с кодом могут строить собственные директивы. [Релиз](https://github.com/mutating/metacode/releases/tag/0.0.1) доступен на GitHub.

## Синтаксис и распределение ответственности

Директива metacode содержит ключ, команду и необязательные аргументы:

```python
# mutating: ignore[comparison]
# fmt: off
# type: ignore[attr-defined]
```

metacode разбирает форму `key: command[arguments]` в записи `ParsedComment`. Аргументы могут содержать распространённые Python-литералы и имена. Потребитель также может явно запросить другие выражения как инертные AST-узлы; metacode никогда их не исполняет.

Вызывающий код передаёт собственный ключ, поэтому посторонние директивы в той же строке игнорируются:

```python
from metacode import parse

comment = "mutating: ignore[comparison] # fmt: off"

print(parse(comment, "mutating"))
#> [ParsedComment(key='mutating', command='ignore', arguments=['comparison'])]
```

Несколько директив, разделённых решётками, могут располагаться в одной физической строке, а обычный текст между совместимыми фрагментами сохраняется без изменений. Каждый инструмент запрашивает свой ключ, поэтому парсер не присваивает команде смысл. Синтаксис общий, а правила применения определяет потребитель.

metacode только разбирает строку с комментарием. Он не читает файлы, не возвращает координаты, не связывает директивы с узлами синтаксиса и не решает, относится ли команда к текущей строке, следующему узлу, блоку или всему файлу.

## Зачем ещё одно соглашение?

metacode не предназначен для замены всех существующих pragmas. Некоторые уже соответствуют его грамматике: [`# type: ignore[code]`](https://typing.python.org/en/latest/spec/directives.html#type-ignore-comments), [`# fmt: off`](https://black.readthedocs.io/en/stable/usage_and_configuration/the_basics.html#ignoring-sections) и `# isort: skip`. Другие — нет: для `# noqa`, `# nosec`, формы `# pragma: no cover` и синтаксиса Pylint `disable=...` понадобятся адаптеры или параллельная поддержка исходных форматов.

Похожие подходы уже существуют. [`doctest` directives](https://docs.python.org/3/library/doctest.html#directives) определяют парсируемый язык комментариев для одной области, а [директивы инструментов Go](https://go.dev/doc/comment#syntax) используют общий синтаксис с пространствами имён.

Комментарий размещает локальную инструкцию рядом с нужным кодом, не влияет на выполнение и не требует импортов. Конфигурация проекта лучше выражает общую политику, а inline-директива может описать исключение для одного выражения.

## Использование в инструментах обработки исходного кода

Токенизаторы и CST-библиотеки находят комментарии, а metacode разбирает их совместимое содержимое. Поэтому инструмент для работы с исходным кодом может разделить обнаружение, разбор и применение правил на отдельные стадии.

Такое разделение способно поддержать нескольких будущих потребителей и не навязывает им единый окружающий фреймворк. Но пока независимые инструменты не приняли одну грамматику, metacode остаётся переиспользуемым соглашением и парсером, а не стандартом экосистемы.

## Что дальше

Проект расширится от разбора отдельных директив до двустороннего слоя управления метаданными в комментариях. Главная цель — предсказуемое взаимодействие инструментов, сохранение обычных комментариев и грамматика, которую можно одинаково реализовать в разных окружениях.
