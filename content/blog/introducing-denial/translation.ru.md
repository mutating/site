title: "Представляем denial: sentinel для отсутствующих значений"
description: "Небольшой именованный sentinel для различения пропущенного значения и явно переданного None."
---

Обычно Python-разработчику достаточно `None`. Но автору библиотеки иногда нужно различить два события: вызывающий код явно передал `None` или не передал ничего. Если использовать `None` для обоих случаев, значения по умолчанию, частичные обновления и многослойные настройки становятся неоднозначными.

[denial](https://github.com/mutating/denial) — крошечная Python-библиотека, которая даёт второму состоянию отдельные имя и тип. В её [первом релизе](https://github.com/mutating/denial/releases/tag/0.0.1) появился `InnerNone`: внутри библиотеки он означает «значение не передано», а обычный `None` остаётся полноценным пользовательским значением.

## Как используется InnerNone

Самый убедительный пример — API, где пропуск означает «унаследовать текущее значение», а `None` — «явно очистить»:

```python
from typing import Union

from denial import InnerNone, InnerNoneType

Timeout = Union[int, None, InnerNoneType]

def resolve_timeout(value: Timeout = InnerNone):
    if value is InnerNone:
        return inherited_timeout()
    return value  # None означает «явно отключено».
```

То же различие встречается в patch API, слоях конфигурации, кэшах, ленивых вычислениях и значениях по умолчанию. `InnerNone` предназначен для внутреннего состояния библиотеки и обычно не должен возвращаться как пользовательское значение.

API намеренно мал: `InnerNone` — общее значение, а `InnerNoneType` можно использовать в аннотациях и проверках `isinstance`. Для проверки идентичности служит `value is InnerNone`.

«Второй `None`» описывает назначение, а не семантику языка Python. В первом релизе `InnerNone` truthy, дополнительные экземпляры `InnerNoneType` можно создавать, а копирование и pickle не сохраняют идентичность экспортированного объекта. Это именованный минимальный sentinel, но ещё не усиленная универсальная фабрика.

## Существующие альтернативы

Однострочная локальная идиома `MISSING = object()` часто остаётся лучшим ответом. denial добавляет стабильный импорт и отдельный публичный тип, но первая версия ещё не улучшает представление, копирование или сериализацию такого подхода.

Стандартный [`dataclasses.MISSING`](https://docs.python.org/3/library/dataclasses.html#dataclasses.MISSING), [`attrs.NOTHING`](https://www.attrs.org/en/stable/api.html#attrs.NOTHING) и undefined-маркеры Pydantic решают ту же неоднозначность внутри своих фреймворков. Они не предназначены для роли общего значения приложения.

Зрелые пакеты [sentinel-value](https://sentinel-value.readthedocs.io/) и [sentinels](https://pypi.org/project/sentinels/) уже предлагают фабрики, читаемые представления и более надёжную сериализацию.

denial 0.0.1 не превосходит эти решения механикой. Его специализация концептуальна и намеренно узка: один независимый от фреймворков маркер внутреннего отсутствия с запоминающимся именем и почти нулевой поверхностью API.

На момент этого релиза [PEP 661](https://peps.python.org/pep-0661/) — предложение стандартного sentinel API — всё ещё имел статус Deferred. Будущий стандарт мог сделать часть этой маленькой задачи универсальной; старым версиям Python и специфической семантике проектов всё равно нужен был бы ответ.

## Что дальше

Следующие релизы дадут маркеру стабильное читаемое представление и позволят приложениям создавать собственные identity-based значения. В планах также единая аннотация для `None` и denial-значений, более чёткое разделение пространств идентификаторов, docstrings для sentinels и усиленная singleton-семантика пользовательских классов.

Порядок важен: сначала назвать отсутствующее состояние, затем сделать его поведение достаточно надёжным для более богатых случаев. Пакет может остаться крошечным и при этом стать менее неожиданным в диагностике, типизации, копировании и сериализации.

denial должен оставаться небольшой зависимостью. Его задача — устранять неоднозначные случаи использования `None` в библиотеках, которые от него зависят.
