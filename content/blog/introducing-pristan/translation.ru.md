Для поддержки отдельно установленных плагинов Python-библиотеке нужно определить контракт, обнаружить реализации, обработать пустой реестр и объединить результаты. Для одной синхронной точки расширения эта инфраструктура легко становится сложнее самой расширяемой функции.

Python entry points решают обнаружение, но не определяют callable-контракт и агрегацию результатов. [Pluggy](https://pluggy.readthedocs.io/en/stable/) предоставляет зрелый plugin manager, однако его порядок вызовов, wrappers, tracing и управление жизненным циклом могут быть лишними для одного типизированного синхронного hook.

[pristan](https://github.com/mutating/pristan) — компактная плагинная Python-библиотека, в которой контракт расширения остаётся обычной типизированной функцией. Эта функция одновременно служит слотом, реестром, fallback и точкой вызова, а установленные плагины лениво обнаруживаются через стандартные Python entry points. [Релиз](https://github.com/mutating/pristan/releases/tag/0.0.1) доступен на GitHub.

## Как работают слоты на основе функций

Декорируйте функцию хоста через `@slot`, и она станет контрактом, реестром, fallback-реализацией и точкой вызова. Плагин — другая обычная функция, декорированная именно этим slot:

```python
from pristan import slot

@slot
def serializers(value) -> dict[str, bytes]:
    ...

@serializers.plugin
def text_serializer(value) -> bytes:
    return str(value).encode()

print(serializers(42))
#> {'text_serializer': b'42'}
```

Вызов slot последовательно запускает все плагины; если их нет, исходное тело функции служит fallback. Каждый плагин остаётся доступен для изолированных тестов.

Аннотация результата slot также определяет, что делать с результатами. Без аннотации они отбрасываются, `list[T]` собирает значения, а `dict[str, T]` — значения под именами плагинов. pristan проверяет сигнатуры при регистрации, а возвращаемые значения — во время выполнения.

Установленные расширения лениво обнаруживаются через Python entry points. Их модули импортируются только при первом обращении к подходящему slot.

## Альтернативы и область применения

По сравнению с Pluggy, pristan требует меньше настройки для более узкого случая: синхронной функции, вызывающей каждый зарегистрированный плагин. Если важнее lifecycle, порядок, wrappers или эволюция протокола, Pluggy остаётся лучшим выбором.

[Stevedore](https://docs.openstack.org/stevedore/latest/) предлагает несколько видов менеджеров, а [Pluginlib](https://pluginlib.readthedocs.io/) использует классовые контракты. Закрытому приложению может быть достаточно словаря и регистрационного декоратора.

## Ограничения

Runtime-проверки ловят многие ошибки контракта, но не доказывают, что каждый вызов slot подойдёт каждому плагину. Плагины выполняются последовательно, одно исключение останавливает dispatch, а в API нет приоритетов, wrappers, пользовательских reducers, async-вызова и удаления плагинов.

Ленивое обнаружение и регистрация защищены от конкурентных изменений, но dispatch не полностью свободен от гонок. Поэтому pristan не гарантирует полную потокобезопасность.

pristan нужен авторам библиотек, которым требуются независимо распространяемые расширения без manager-класса для каждого hook. Его slots позволяют держать опциональные возможности вне ядра, не определяя окружающую архитектуру.

## Что дальше

Проект поддержит больше плагинных контрактов и сделает жизненный цикл и конкурентное поведение предсказуемее, не усложняя компактный API на основе функций.
