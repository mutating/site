Чтобы отдельно установленные пакеты могли расширять Python-библиотеку, её автору нужно определить возможности плагинов, обнаружить их, зарегистрировать функции, обработать отсутствие реализаций и объединить результаты. Когда эти части определены отдельно, callable-контракт труднее увидеть, проверить типами и протестировать. Для небольшой синхронной точки расширения вспомогательная инфраструктура легко становится сложнее самой расширяемой функции.

Python entry points решают задачу обнаружения пакетов, но не определяют callable-контракт и способ объединения нескольких результатов. [Pluggy](https://pluggy.readthedocs.io/en/stable/) предоставляет зрелый plugin manager с порядком вызовов, wrappers, tracing и управлением жизненным циклом. Небольшой библиотеке всё равно приходится либо самостоятельно писать недостающую связующую логику, либо принимать модель менеджера, возможности которого избыточны для одного типизированного синхронного hook.

[pristan](https://github.com/mutating/pristan) — компактная плагинная Python-библиотека, в которой контракт расширения остаётся обычной типизированной функцией. Эта функция одновременно служит слотом, реестром, fallback и точкой вызова, а установленные плагины лениво обнаруживаются через стандартные Python entry points. [Релиз](https://github.com/mutating/pristan/releases/tag/0.0.1) доступен на GitHub.

## Как работают слоты на основе функций

Декорируйте функцию хоста через `@slot`, и она станет контрактом, реестром, fallback-реализацией и точкой вызова. Плагин — другая обычная функция, декорированная именно этим slot:

```python
from pristan import slot

@slot
def serializers(value) -> dict[str, bytes]:
    ...

@serializers.plugin
def text_serializer(value) -> bytes:
    return str(value).encode()

print(serializers(42))
#> {'text_serializer': b'42'}
```

Вызов `serializers(value)` последовательно запускает все зарегистрированные плагины. Если их нет, работает исходное тело функции. Декоратор плагина возвращает исходную функцию, поэтому реализацию можно тестировать напрямую.

Аннотация результата slot также определяет, что делать с результатами. Без аннотации они отбрасываются, `list[T]` собирает значения, а `dict[str, T]` — значения под именами плагинов. pristan проверяет сигнатуры при регистрации, а возвращаемые значения — во время выполнения.

Независимо распространяемые расширения лениво обнаруживаются через стандартные entry points Python. Первая значимая операция slot загружает модули из своей группы, а импорт этих модулей активирует декораторы. Стоимость обнаружения и побочные эффекты импорта откладываются до первого обращения.

## Альтернативы и область применения

По сравнению с Pluggy, pristan требует меньше настройки для более узкого случая: синхронной функции, вызывающей каждый зарегистрированный плагин. Если важнее lifecycle, порядок, wrappers или эволюция протокола, Pluggy остаётся лучшим выбором.

[Stevedore](https://docs.openstack.org/stevedore/latest/) предоставляет несколько видов менеджеров, а [Pluginlib](https://pluginlib.readthedocs.io/) сосредоточен на классовых контрактах. В закрытом приложении может быть достаточно небольшого словаря и регистрационного декоратора.

## Ограничения

Runtime-проверки ловят многие ошибки контракта, но не доказывают, что каждый возможный вызов slot подойдёт каждому плагину. Плагины выполняются последовательно, и одно исключение останавливает цепочку. В API нет приоритетов, wrappers, пользовательской агрегации результатов, async-dispatch и удаления плагинов.

Ленивое обнаружение и регистрация защищены от конкурентных изменений, но dispatch не полностью свободен от гонок. Поэтому pristan не гарантирует полную потокобезопасность.

pristan нужен авторам библиотек, которые хотят независимо распространяемые расширения, но не хотят превращать каждый hook в manager-класс. В более крупной системе такие slots позволяют держать опциональные возможности вне ядра и не предрешать окружающую архитектуру.

## Что дальше

Проект будет расширять набор контрактов, которые способен выразить slot, сохраняя компактный API на основе функций. Другой приоритет — более предсказуемый жизненный цикл и конкурентное поведение при одновременном обнаружении, изменении и вызове плагинов.
