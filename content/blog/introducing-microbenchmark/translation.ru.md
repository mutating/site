Пример с `timeit` становится неудобным, когда нескольким измерениям нужны имена, общий запуск, машиночитаемые результаты и порог ошибки. Полноценные системы бенчмарков могут требовать больше настройки и статистики, чем нужно для небольшой проверки библиотеки.

[`timeit`](https://docs.python.org/3/library/timeit.html) предоставляет средства измерения, но не модель сценариев или бюджет для CI. [pyperf](https://pyperf.readthedocs.io/) и [pytest-benchmark](https://pytest-benchmark.readthedocs.io/en/latest/) дают более строгую статистику и изоляцию. Небольшим проектам могут быть нужны именованные сериализуемые измерения без полноценной системы бенчмарков.

[microbenchmark](https://github.com/mutating/microbenchmark) — лёгкая Python-библиотека для структурированных измерений небольшого масштаба. Она представляет сценарии, группы и результаты бенчмарков обычными Python-объектами, которые можно объединять, исследовать, сериализовать и проверять по простому бюджету производительности. [Релиз](https://github.com/mutating/microbenchmark/releases/tag/0.0.1) доступен на GitHub.

## Основной API

`Scenario` хранит callable, позиционные аргументы, имя, документацию и число наблюдений вместе. `run()` выполняет необязательные прогревочные вызовы, а затем отдельно измеряет каждое выполнение через `perf_counter()` по умолчанию.

```python
from microbenchmark import Scenario

def build_list():
    return list(range(1000))

scenario = Scenario(build_list, name="build_list", number=500)
result = scenario.run()

print(result.mean)
print(result.best)
print(result.worst)
```

Получается `BenchmarkResult`, сохраняющий все длительности вместо немедленного сведения запуска к одному числу. Он предоставляет среднее, лучший и худший результаты. Свойства `p95` и `p99` возвращают усечённые наборы — самые быстрые 95 или 99 процентов замеров, — а не привычные скалярные перцентили задержки.

Сложение сценариев создаёт плоский упорядоченный `ScenarioGroup`. Результаты сериализуются в JSON, но десериализация не восстанавливает исполняемые сценарии.

Вызов `.cli()` добавляет benchmark-скрипту параметры `--number` и порог ошибки `--max-mean`; отдельная команда не устанавливается.

Библиотека типизирована и не имеет runtime-зависимостей.

## Альтернативы и компромиссы

[`timeit`](https://docs.python.org/3/library/timeit.html) остаётся правильным выбором для разового измерения. Группировка операций и автоматический подбор длительности также уменьшают влияние самого таймера.

[pyperf](https://pyperf.readthedocs.io/) добавляет калибровку циклов, worker-процессы и статистические сравнения; [pytest-benchmark](https://pytest-benchmark.readthedocs.io/en/latest/) объединяет проверки регрессий с pytest; [Airspeed Velocity](https://asv.readthedocs.io/) отслеживает производительность по коммитам.

Отдельное измерение каждого вызова увеличивает влияние таймера и Python-вызова. Здесь нет автоматической калибровки, изоляции процессов или сравнения с baseline, а `--max-mean` чувствителен к железу и нагрузке CI.

## Для кого предназначен microbenchmark

microbenchmark предназначен авторам библиотек, которым нужны несколько переиспользуемых performance-сценариев рядом с кодом. Для более строгих статистических требований лучше выбрать полноценную систему бенчмарков.

## Что дальше

Проект упростит работу из Python и командной строки, оставаясь лёгким инструментом, а не системой статистического бенчмаркинга.
