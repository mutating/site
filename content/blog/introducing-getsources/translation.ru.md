Инструментам мутации, преобразования и интроспекции нужно получить исходный текст из объекта Python-функции, прежде чем разбирать или изменять его. Стандартная библиотека хорошо работает с обычными модулями, но интерактивное определение может оказаться недоступным, а вложенная функция сохраняет отступ внешней области. Поэтому следующий этап парсинга способен завершиться ошибкой, хотя исходная функция является корректным Python-кодом.

Стандартное решение — [`inspect.getsource()`](https://docs.python.org/3/library/inspect.html#inspect.getsource), а [dill](https://dill.readthedocs.io/en/latest/dill.html#module-dill.source) и [sourceinspect](https://pypi.org/project/sourceinspect/) поддерживают больше интерактивных окружений. Их API и результаты различаются, и ни один из них не задаёт для проекта общий порядок fallback-механизмов и нормализации отступов. Без общего адаптера каждому потребителю AST или CST приходится самостоятельно реализовывать и тестировать эти правила.

[getsources](https://github.com/mutating/getsources) — небольшая Python-библиотека с единым API для получения и нормализации этого текста. Она объединяет `inspect` с резервным механизмом на основе `dill` и отдельно умеет удалять общий начальный отступ. [Релиз](https://github.com/mutating/getsources/releases/tag/0.0.1) доступен на GitHub.

## Получение и нормализация исходника

`getsource(function)` сначала обращается к стандартной библиотеке. Если `inspect.getsource()` поднимает `OSError`, используется `dill.source.getsource()`, способный восстановить обычные определения и lambda из истории классической интерактивной сессии Python.

`getclearsource(function)` затем снимает ведущий отступ, унаследованный от внешнего класса или функции. Вложенное определение корректно внутри исходного блока, но может упасть при прямой передаче в `ast.parse()`. Очищенная форма сохраняет относительные отступы тела и делает фрагмент пригодным для верхнего уровня.

```python
from getsources import getclearsource

class Parser:
    @staticmethod
    def parse(value):
        return int(value)

print(getclearsource(Parser.parse))
#> def parse(value):
#>     return int(value)
```

Полученный текст можно разобрать, не восстанавливая окружающий класс.

Библиотека сосредоточена на функциях, определённых в Python, включая методы и lambda-выражения. Это не универсальный инспектор для модулей, классов, builtins, C-расширений или произвольных callable-объектов.

Есть ещё одно важное ограничение. Lambda принимается как объект функции, но getsources не выделяет само lambda-выражение из окружающего statement. Исходник вида `handler = lambda value: value + 1` может вернуться вместе с присваиванием.

## Как выбрать инструмент восстановления исходника

Для обычного файлового кода проекту может быть достаточно `textwrap.dedent(inspect.getsource(function))`. `inspect.getsourcelines()` также возвращает номера строк и поддерживает больше видов объектов, а прямое использование [dill](https://dill.readthedocs.io/en/latest/dill.html#module-dill.source) даёт больше настроек восстановления.

[sourceinspect](https://pypi.org/project/sourceinspect/) поддерживает больше интерактивных оболочек и предоставляет более широкий API инспекции. [executing](https://github.com/alexmojaki/executing) и [stack-data](https://github.com/alexmojaki/stack_data) лучше подходят, когда анализ начинается с runtime-frame или traceback. [cloudpickle](https://github.com/cloudpipe/cloudpickle) решает другую задачу: переносит исполняемое поведение между процессами, а не восстанавливает читаемый исходник.

Интерактивное восстановление остаётся best-effort. У динамического кода из `exec` или `eval` может не быть надёжного происхождения, сопоставление lambda с историей может быть неоднозначным, а файл на диске — уже не соответствовать загруженному code object. Это восстановление исходника, а не декомпиляция bytecode.

## Для чего предназначен getsources

Пакет предназначен для AST- и CST-библиотек, пользователи которых могут передать объект функции из модуля, вложенной области или классического REPL. Он даёт этим потребителям единый API исходного кода и скрывает различия между окружениями инспекции.

## Что дальше

Проект будет надёжнее восстанавливать неоднозначные или сложные определения функций и предоставлять устойчивые идентификаторы исходного кода другим инструментам, сохраняя публичный API сосредоточенным на получении исходника.
