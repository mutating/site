# throng_api

HTTP API и контроллер заданий для выполнения команд `throng` на подключённых
компьютерах. API и контроллер запускаются в одном процессе. Очередь, назначения,
резервирование ресурсов, отмены и результаты сохраняются в SQL-базе.

Плагин `throng` и агент компьютера разрабатываются отдельно. Интеграционные
тесты используют имитатор агента. Личный кабинет находится в соседнем пакету API
каталоге [web](../web/README.md), запускается отдельным
Python-сервисом в корне поддомена платформы и имеет собственные браузерные и серверные тесты.
Для API и кабинета есть общий запуск и единый production-сервис systemd: см.
[развёртывание](../../docs/deployment.md).

Базовый адрес production API: `https://api.mutating.tech/v1`.

`GET /v1/organization-directory?q=lab&limit=20&offset=0` возвращает личный каталог
организаций и действующих адресных приглашений. Требуется личный токен со scope
`read`. Ответ: `{items, total, total_all}`; `X-Total-Count` совпадает с `total`.
`items` — объединение `{kind: "company", group: 1|2, company}` и
`{kind: "invitation", group: 0, invitation}`. `total_all` считает только доступные
пользователю записи без фильтра; открытые ссылки, чужие/истёкшие/отозванные/принятые
приглашения и удалённые организации в каталог не входят. Членство имеет приоритет
над оставшимся приглашением той же организации, несколько приглашений дают одну строку.
Поиск по подстроке имени использует NFC и Unicode casefold, обрезает пробелы
в запросе и воспринимает `%`, `_` и escape-символы буквально. Используется текущее
название организации, включая превью приглашений. Сначала приглашения, затем
организации, созданные самим пользователем, затем прочие членства независимо от
роли. В каждой группе — общее количество компьютеров по убыванию (включая офлайн
и выключенные), затем нормализованное название с естественным порядком чисел,
затем ID организации. Фильтрация и сортировка предшествуют пагинации.
`q` ограничен 200 символами, `limit` — 1–200 (по умолчанию 20), `offset` — 0…2⁶³−1.
Миграция `0009` заполняет поля поиска и порядка для существующих имён; создание
и переименование поддерживают их автоматически в SQLite и PostgreSQL.

Результаты benchset хранятся в `benchmark_results` (миграции `0008`, `0018`). CRUD:
`POST /v1/benchmark-results`, `GET /v1/benchmark-results?computer_id=<uuid>`,
`GET/PATCH/DELETE /v1/benchmark-results/<uuid>`. Также доступен
`GET /v1/computers/<uuid>/benchmark-results`. Запись содержит `id`, `run_id`, `created_at`,
`computer_id`, `benchmark_name`, конечное неотрицательное `number` и строгую
SemVer 2 `benchmarker_version`. Для проверки и сравнения версий используется
библиотека `semver`. Без `run_id` каждый POST создаёт новый запуск, в том числе для той же
версии и с тем же результатом. Опциональный UUID `run_id` обозначает конкретный
запуск: клиент генерирует новый ID для нового запуска и повторяет его при
повторной отправке. Идентичность результата задаётся тройкой компьютер/имя/run_id.
Повтор с тем же ID и данными возвращает прежнюю запись; изменение результата
или версии для существующего запуска возвращает 409. PATCH меняет число
конкретной записи. `created_at` — время первого сохранения запуска сервером в UTC;
интерфейс показывает его в часовом поясе браузера. Для записей до миграции `0018`
сохраняется исходная дата создания; ранее перезаписанные результаты восстановить нельзя.
Откат `0018` запрещён, если он потеряет отдельные запуски или их идентификаторы.
Списки по умолчанию возвращают последнее измерение каждого имени из
наибольшей semver-версии, `latest_only=false` — все сохранённые запуски.
Порядок API: версия SemVer, имя, время сохранения, ID запуска (по возрастанию);
интерфейс истории сортирует по времени от новых к старым. При равном semver
precedence build metadata разрешает ничью лексикографически по полной версии.

Агент отправляет каждый завершённый тест через
`PUT /agent/v1/benchmark-results` с `benchmarker_version`, опциональным `run_id`
и массивом `results`
из `{benchmark_name, number}`. Компьютер определяется по credential; ID из
тела не принимается. Сессия вычислений не требуется, device proof для
подтверждённых устройств обязательна. Несколько измерений в одном запросе
записываются транзакционно с общими `run_id` и `created_at`; частично невалидный
или конфликтующий запрос не меняет прежние данные. Результаты одного запуска
можно досылать отдельными запросами с тем же `run_id`. Старые агенты могут
отправлять прежний формат без `run_id`: каждый такой запрос создаёт новый запуск;
для устранения дублей при сетевых повторах агенту нужно передавать `run_id`.
Права CRUD совпадают с правами компьютера и `resources.read`/`resources.manage`.
Для тестирования Swift-клиента на macOS задайте `POWER_CELL_BENCHMARK_CLI`
путём к `powercell-dev` и запустите `test_benchmark_swift_client.py`.

## Запуск

Нужны обычный CPython 3.12 и `uv`. Поддерживаемый диапазон Python начинается с 3.11;
локальное окружение зафиксировано на 3.12 в `.python-version`.

```sh
uv sync --frozen
cp .env.example .env  # только если собственного .env ещё нет
npm --prefix ../.. ci
npm --prefix ../.. run build:web
uv run python ../../deploy/run.py
```

Общая команда применяет миграции, запускает API на `127.0.0.1:8000`, ждёт его
готовности и поднимает кабинет на `http://127.0.0.1:8001/`. Ctrl+C
останавливает оба процесса. Если один компонент неожиданно завершается, общий
процесс останавливает второй и возвращает ошибку; на сервере systemd перезапускает
весь сервис. Для запуска только API остаётся `uv run throng-api serve`.

`serve` применяет миграции Alembic и запускает Uvicorn вместе с контроллером.
По умолчанию используются SQLite в `data/throng.db`, файлы в `data/artifacts`
и адрес `127.0.0.1:8000`.

- Swagger UI: <http://127.0.0.1:8000/docs>
- ReDoc: <http://127.0.0.1:8000/redoc>
- OpenAPI: <http://127.0.0.1:8000/openapi.json>
- Проверки процесса и готовности: `/health/live`, `/health/ready`.

Необязательный запуск только API в контейнере (production-деплой использует systemd):

```sh
docker compose up --build
```

И база, и артефакты сохраняются в томе `throng-data`. Порт публикуется только на
loopback. Для удалённого доступа разместите сервис за HTTPS-прокси с ограничениями
размера запросов, частоты регистрации/входа и таймаутом long polling больше 25 секунд.

Миграции можно запускать отдельно:

```sh
uv run throng-api migrate
uv run uvicorn throng_api.app:app --host 127.0.0.1 --port 8000
```

При прямом запуске Uvicorn схема должна уже существовать. Приложение не вызывает
`create_all()` и проверяет наличие мигрированной базы перед началом работы.
Миграции требуют подключения к БД для переноса данных и проверки текущей схемы.
Режим Alembic `--sql` отклоняется до генерации SQL; используйте `throng-api migrate`
либо `alembic upgrade head` с настроенным `THRONG_DATABASE_URL`.

## Первый запрос

```sh
curl -X POST http://127.0.0.1:8000/v1/users \
  -H 'Content-Type: application/json' \
  -d '{"email":"alice@example.com","password":"replace-with-a-long-password","first_name":"Alice","last_name":"Example","nickname":"alice"}'

curl -X POST http://127.0.0.1:8000/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"alice@example.com","password":"replace-with-a-long-password"}'
```

Для последующих запросов используется `Authorization: Bearer <access_token>`.
Swagger UI поддерживает кнопку Authorize. Регистрация и вход не требуют токена.

В Swagger выберите **Authorize → AccessToken** и вставьте только значение
`access_token`, без слова `Bearer`. Для `/agent/v1/*` используется отдельное поле
**AgentCredential**: туда вводится credential компьютера, а в параметр
`X-Agent-Session` конкретного запроса — UUID активной сессии. Для создания и чтения
сессии этот заголовок не нужен. Поля бинарной загрузки отправляют файл непосредственно
в HTTP-теле с `Content-Type: application/octet-stream`.

Вход выдаёт случайный непрозрачный credential `thr_…` со всеми тремя scopes на 24 часа
по умолчанию (`THRONG_LOGIN_TOKEN_SECONDS`). Его хэш хранится в `login_sessions`;
каждый запрос проверяет срок, отзыв и текущие права. Refresh-токена нет: после
истечения срока нужно войти снова. `/auth/login` сохраняет поля `access_token`,
`token_type` и `token`; метаданные `token` описывают сессию (`id`, `user_id`, `name`,
`scopes`, `created_at`, `expires_at`, `revoked_at`), без владения API-токеном.
Отзыв отдельной сессии — `DELETE /v1/auth/sessions/{id}` (только своей), выход из
браузера — `DELETE /v1/auth/session`. Сессии всегда имеют конечный срок и не
доступны через CRUD `/access-tokens`.

API-токены хранятся независимо, в `access_tokens`. Через `/v1/access-tokens` можно
выпустить токен с выбранными scopes и сроком от 60 секунд до года либо без срока.
Новые личные API-токены начинаются с `SELF-`, организационные — с `ORG-`.
После префикса идут 64 случайных шестнадцатеричных символа (`0–9`, `a–f`):
только латинские буквы и цифры, 256 бит случайности. Уже выданные токены `thr_…`
продолжают работать до отзыва или истечения срока; права определяются записью
в БД, а не префиксом.
Для отзыва — `PATCH /v1/access-tokens/{id}` с `{"revoke":true}` либо `DELETE`
этого ресурса. Выход или отзыв сессии не отзывает API-токены; смена пароля, как
и прежде, отзывает все выданные пользователем доступы, включая бессрочные токены.

Кабинет использует реестр `GET /v1/api-tokens`: владелец (`user_id` либо `company_id`)
и публичный профиль выпустившего участника (`issuer`, без email) возвращаются раздельно.
Фильтры `user_id` и `company_id` взаимоисключающие; `limit`/`offset` применяются после
проверки доступа, общее количество возвращается в `X-Total-Count`.
`POST /v1/api-tokens` принимает ровно одного владельца, `name`, `scopes` и
`expires_in_seconds`, атомарно создаёт владение и токен и однократно возвращает `token`.
Срок — от 60 секунд до 365 дней (31 536 000 секунд); по умолчанию 24 часа.
Явное `"expires_in_seconds": null` выпускает бессрочный токен: `expires_at` в
ответе равен `null`; он действует до отзыва. Отсутствующее поле сохраняет срок
по умолчанию. Ноль, отрицательные значения и конечный срок больше года отклоняются.
Для организации чтение требует `tokens.read`, выпуск и отзыв — `tokens.manage`;
эти права не зависят от доступа к списку участников. Выпуск требует личного токена
со scope `manage`; расширить scopes относительно текущего токена нельзя.

Миграция `0017` переносит явно помеченные личные входы в `login_sessions`, API-токены
оставляет в `access_tokens`. Старые записи `legacy` с неизвестным назначением
и нетипичные записи `login` (владение компанией либо несовпадение владельца с автором)
сохраняются в отдельной `legacy_credentials`, без угадывания по имени и без изменения
прав, хэшей, дат или ID. Они продолжают авторизовать и доступны через совместимый
CRUD `/access-tokens`. Сессии больше не зависят от `token_ownerships`.
Реестр показывает только `api`, включая API-токены с именем `login`.
Миграция обратима, но при наличии бессрочных токенов откат к `0016` отклоняется
до изменения схемы: старая версия не умеет хранить отсутствие срока. Для отката
такие записи требуется удалить; один отзыв не меняет их `expires_at`.
Ответы реестра и выпуска — `no-store`; секретов и хэшей в списке нет.

`GET /v1/auth/check` проверяет личный или корпоративный токен через единый
интерфейс без создания ресурсов. Требуются одновременно scopes `read` и `execute`;
для организации — также текущие права издателя `execution.read` и `execution.run`.
Успех возвращает `{"valid":true,"scopes":["execute","read"]}` (все scopes токена),
недействительный токен — `401`, недостаточные права — `403`.
Для клиентской авторизации `/v1`, включая выполнение команд, ответ `401` содержит
машинный `code`: `token_invalid` (невалидный доступ) либо `token_expired` (истёкший).
Клиенту следует использовать `code` для выбора сообщения в интерфейсе, а не
сопоставлять текст `detail`. Отозванный и одновременно истёкший токен остаётся
`token_invalid`; бессрочные токены не переходят в `token_expired`.
Подробный контракт и границы проверки: [проверка токена](docs/token-check.md).

## Учётные записи и права

Организации поддерживают совместное управление и приглашения. Через
`POST /v1/memberships` менеджер добавляет пользователя: `company_id` и либо
`user_id`, либо `identifier` (точный email/ник, регистр не важен), `role` и
необязательные `permissions`. Поиск по точному логину доступен менеджеру через
`GET /v1/companies/{id}/users/lookup?identifier=…`; общего каталога нет.

Список `GET /v1/memberships?company_id=…` содержит роль, `permissions`,
фактические `effective_permissions` и профиль `user`: ФИ, ник, версию аватара.
Чужие email и приватные поля не выдаются. Есть `limit`, `offset`, `X-Total-Count`.
Аватар: `GET /v1/memberships/{id}/avatar`, с проверкой права чтения участников.
Ответы списка/карточки организации содержат `my_role`, `my_permissions`, `my_membership_id`.

`permissions=null` наследует роль; массив задаёт полный набор отдельных разрешений,
включая пустой массив. В `PATCH /memberships/{id}` можно менять роль или права.
Смена роли без нового массива включает её стандартные права. Создатель всегда
имеет полный доступ; только создатели назначают администраторов/создателей.
Последний создатель защищён от удаления/понижения. Делегированный менеджер может
выдавать обычным участникам только те разрешения, которые имеет сам.

| Разрешение | Действия |
| --- | --- |
| `members.read` | Список, профили и аватары участников |
| `members.manage` | Участники, их права и приглашения |
| `resources.read` | Компьютеры, ресурсы, сводки и история мощностей |
| `resources.manage` | Изменение компьютеров, ресурсов, владения, credentials и подключений |
| `execution.read` | Изоляты, команды, результаты, операции и артефакты |
| `execution.run` | Выполнение/отмена задач и изменение артефактов |
| `tokens.read` | Метаданные токенов и связей владения |
| `tokens.manage` | Выпуск, изменение и отзыв токенов |
| `company.manage` | Настройки организации |

Стандартный участник имеет `members.read`, `resources.read`, `execution.read`,
`execution.run`, `tokens.read`; администратор и создатель — все девять. Базовое
название своей организации видно каждому участнику. API проверяет права при
каждом запросе, включая коллекции и корпоративные токены, дополнительно к scopes
токена. Уменьшение прав/выход отзывает выпущенные участником корпоративные токены
и его ожидающие приглашения.

`POST /v1/invitations` принимает `company_id`, `role`, `permissions`,
необязательный `identifier`, `expires_in_seconds` (1 час–30 дней, по умолчанию 7 дней).
Можно пригласить по email до регистрации; существующий ник привязывает приглашение
к конкретному аккаунту. Без адресата создаётся одноразовая ссылка. Создание выдаёт
`token` один раз; в БД хранится хэш. Обычные списки секрет ссылки не возвращают.

- `GET /invitations` — ожидающие адресные приглашения текущего пользователя.
- `GET /invitations?company_id=…` — история для менеджера участников.
- `GET /invitations/link/{token}` — просмотр после входа.
- `POST /invitations/{id}/accept` или `/invitations/link/{token}/accept` — принятие.
- `POST /invitations/{id}/decline` — отказ адресного получателя.
- `POST /invitations/{id}/link` — новая ссылка, старая перестаёт действовать.
- `DELETE /invitations/{id}` — отзыв.

У этих сокращённых путей префикс `/v1`. Принятие атомарно создаёт членство,
проверяет адресата и право отправителя выдать доступ. Срок, отзыв и повторное
использование проверяются сервером; существующее членство не перезаписывается.
Удаление пустой организации отзывает ожидающие приглашения, сохраняя историю.
Письма автоматически не отправляются: приглашение появляется в кабинете,
отправитель передаёт ссылку вручную. Нужна миграция `0007`, которую `serve` применяет сам.

Регистрация требует только email и пароль. `first_name`, `last_name` и `nickname`
необязательны; отсутствующие ФИ сохраняются как пустые строки, ник — как `null`.
Вход принимает `{"login":"email-или-ник","password":"…"}` без учёта регистра логина;
прежнее поле `email` также поддерживается. В `PATCH /users/{id}` ник можно убрать
значением `null`, ФИ — пустой строкой.

Аватар текущего пользователя доступен через `GET`, `PUT`, `DELETE /v1/users/me/avatar`.
`PUT` принимает файл непосредственно в теле: статичный PNG/JPEG/WebP до 2 МиБ и 16 Мп.
API нормализует изображение в квадратный WebP 512×512, удаляет метаданные и возвращает
обновлённый профиль с `avatar_version`. Чтение требует личного токена.

CRUD доступен для `/v1/users`, `/companies`, `/memberships`, `/computers`,
`/computer-ownerships`, `/access-tokens`, `/token-ownerships`. Списки ресурсов
поддерживают `limit` (максимум 200) и `offset`, кроме списка пользователей, который
возвращает только текущую учётную запись. `/users/me` возвращает профиль.
`offset` должен лежать в диапазоне от 0 до `2^63 - 1`.
Текстовые поля принимают корректный Unicode без NUL; недопустимый текст возвращает
`422`. Произвольные байты, включая бинарные логи, передаются через артефакты.
Пакет `/v1/commands/results` имеет предел размера ответа
`THRONG_MAX_RESULTS_RESPONSE_BYTES` (по умолчанию 16 МиБ). Если запрошенные
результаты, с учётом повторных ID, его превышают, API возвращает `422`;
разделите список на более мелкие запросы или скачайте логи как артефакты.

- Пользователь читает и меняет собственный профиль. Общего каталога пользователей нет.
  Системный администратор управляет справочником типов ресурсов; эта роль не даёт
  доступа к чужим компьютерам, профилям или данным компаний.
- Компания создаётся атомарно с членством создателя. Роли: `creator`, `admin`, `user`.
  Создатель управляет привилегированными членствами; компания должна сохранять хотя
  бы одного создателя. Несколько создателей допускаются для передачи управления.
- Члены компании могут использовать её изоляты и читать результаты. Администраторы
  управляют компьютерами, настройками компании и токенами. Удаление компании
  доступно создателю.
- Права API-токена: `read`, `execute`, `manage`. Они дополнительно ограничены
  владельцем ресурса и членством. Выпуск токенов требует личного токена с `manage`;
  выдать отсутствующие у него права нельзя.
- Корпоративный bearer-токен действует от имени компании. Его можно делегировать:
  предъявителю не требуется собственное членство, поскольку API устанавливает
  личность только по токену. При каждом запросе проверяется, что выпустивший токен
  пользователь по-прежнему имеет право `tokens.manage` в компании и разрешение
  на конкретное запрашиваемое действие.
- Изменение пароля требует личного токена со всеми тремя scopes, чтобы ограниченный
  делегированный токен не мог получить полные права через сброс пароля и новый вход.
- Компания и пользователь — взаимоисключающие владельцы. XOR, внешние ключи,
  уникальность членства и единственное владение компьютером проверяет сама БД.
- Пароли хэшируются Argon2id. Случайные API- и агентские токены хранятся как SHA-256
  хэши. Секрет возвращается только при выпуске. Изменение пароля отзывает токены,
  выпущенные пользователем; потеря административного членства отзывает выпущенные
  им токены соответствующей компании.
- Связь владения токеном можно изменить только после удаления прикреплённых токенов.
  Удаление этой связи удаляет её токены. Удаление пользователя/компании с зависимыми
  ресурсами или историей возвращает `409`; история выполнения автоматически не стирается.
  Другие участники и связи владения токенами также блокируют удаление компании;
  при удалении пустой компании удаляется только собственное членство её создателя.

Компьютер создаётся вместе с владельцем. Если указан `company_id`, требуются права
администратора этой компании. Без него владельцем становится пользователь либо
компания текущего токена. Переназначение/удаление владения разрешено только без
зарезервированных ресурсов и отзывает credential агента. Для компьютера без владельца
новую связь может создать его первоначальный регистратор. Удаление компьютера с
историей выполнения запрещено внешними ключами; его можно отключить через `enabled=false`.
Отключение прекращает выделение новых изолятов, оставляя существующие доступными.

В текущей модели личный запрос использует личный пул, корпоративный — пул компании.
Предоставление компьютеров незнакомым пользователям и объединение пулов не включены.
При создании изолята личным токеном можно явно указать `company_id` компании,
в которой пользователь состоит: тогда используется только её пул. При нехватке
доступных ресурсов чужие пулы не используются. Членство не открывает доступ к личным
компьютерам коллег. Отправка команды в чужой изолят возвращает `404`, даже если
известен ключ ранее успешного запроса. Все ответы `404` имеют одинаковое тело
`{"detail":"Resource not found"}`, чтобы различия внутренних проверок не раскрывали
существование чужих ресурсов и тип их владельца. После удаления членства тот же личный токен
больше не может создавать изоляты или отправлять команды в пул этой компании.

## Компьютерные ресурсы

Список `/v1/computers` поддерживает фильтры `user_id` **или** `company_id`,
`only_available=true` и возвращает `X-Total-Count` после фильтрации до пагинации.
Список `/v1/memberships` поддерживает `user_id` для получения собственной роли.

Для графиков кабинета добавлены `/v1/users/{user_id}/resources/availability-history`
и `/v1/companies/{company_id}/resources/availability-history`. Они показывают
CPU/RAM и резервы только доступных компьютеров, учитывая периоды связи и истечение lease.
История начинается с миграции `0005`; более ранние значения не восстанавливаются.
Протокол агента и политика выполнения задач этой доработкой не меняются.

CPU и память хранятся в `computer_resources`. Для каждого компьютера и типа ресурса
БД допускает ровно одну запись. `total` — выделенная сервису мощность, `occupied` —
резерв под изоляты, `free = total - occupied`. Это учёт резервов, а не загрузка ОС.
CPU измеряется в millicores (1000 = одно ядро), память — в байтах.
Старые поля компьютера `cpu_millis`, `memory_bytes`, `reserved_cpu`, `reserved_memory`
вычисляются из этих записей. Миграция переносит существующие мощности и резервы.

Каталог `/v1/resource-types` доступен только системному администратору с личным
токеном. Права создателя или администратора компании этого доступа не дают.
Назначение и отзыв системной роли выполняются на хосте сервера:

```sh
uv run throng-api system-admin <user-uuid>
uv run throng-api system-admin <user-uuid> --revoke
```

CRUD ресурсов компьютера доступен владельцу или администраторам компании;
члены компании могут читать её ресурсы и отчёты. Сводки и история:

- `/v1/users/{user_id}/resources/summary` и `/history`;
- `/v1/companies/{company_id}/resources/summary` и `/history`;
- `/v1/computer-resources/{resource_id}/history`.

История сохраняет владельца на момент изменения, включая передачу и удаление
ресурса. Для графика возвращаются начальное состояние и изменения за интервал
`[from, to)`, с пагинацией по сохранённой ревизии.
Полный контракт, единицы, ограничения и примеры запросов — в
[описании ресурсов](docs/resources.md). Все ручки также представлены в `/docs`.

## Выполнение

1. Загрузить исходное состояние: `POST /v1/artifacts`, бинарное тело,
   необязательные query-параметры `filename` и `company_id`.
2. Создать изолят: `POST /v1/isolates` с `Idempotency-Key`.
3. Ожидать `ready` через `GET /v1/isolates/{id}`.
4. Послать команду: `POST /v1/isolates/{id}/commands` с `Idempotency-Key`.
5. Получать статусы и результаты пакетами.
6. Продлевать срок жизни изолята через `POST /v1/isolates/{id}/renew` и
   уничтожить его через `DELETE /v1/isolates/{id}` после использования.

Пример запроса создания изолята:

```json
{
  "state_artifact_id": "<uuid загруженного состояния>",
  "image": "python:3.12",
  "os": "linux",
  "architecture": "amd64",
  "runtime": "oci",
  "cpu_millis": 1000,
  "memory_bytes": 536870912,
  "disk_bytes": 1073741824
}
```

Владелец состояния должен совпадать с владельцем изолята. `image` — идентификатор
среды, который интерпретирует агент. API его не загружает и не запускает.
Если `image` не передан, используется `ubuntu`. Явные `null` и пустая строка
недопустимы.
Для `runtime: "powercell-ubuntu-arm64-v1"` можно передать `image: "ubuntu"`
или `image: "actions"`: API раскроет их в `ubuntu:24.04` и
`ghcr.io/actions/actions-runner:latest`. В ответах и заданиях агенту будет полная
ссылка; явные теги и digest также поддерживаются. Политика совместимости — в
[описании Power Cell](docs/powercell.md#capacity-and-isolation).
`cpu_millis=1000` соответствует одному логическому CPU; память и диск заданы в байтах.
ОС, архитектура и runtime сопоставляются с компьютером точным сравнением строк.
Агент обязан самостоятельно применять указанные лимиты и проверять реальную доступность.

Пример команды:

```json
{"command":"pytest -q","shell":false,"cwd":".","env":{},"timeout_seconds":600}
```

Команды в одном изоляте выполняются последовательно в порядке приёма API.
`cwd` задаётся относительно корня изолята. Семантика исполнения описана в
[протоколе агента](docs/agent-protocol.md).

| Метод и путь | Назначение |
|---|---|
| `POST /v1/commands/statuses` | Статусы; тело `{"ids":["<uuid>"]}` |
| `POST /v1/commands/results` | Статусы и результаты; такое же тело |
| `POST /v1/commands/cancel` | Пакетная внешняя отмена; такое же тело |
| `GET /v1/commands/{id}` | Описание отдельной команды |
| `GET /v1/commands/{id}/result` | Результат отдельной команды |
| `POST /v1/commands/{id}/cancel` | Отмена отдельной команды |
| `POST /v1/isolates/{id}/snapshots` | Снимок простаивающего изолята; нужен `Idempotency-Key` |
| `GET /v1/operations/{id}` | Состояние операции создания снимка |
| `GET /v1/artifacts/{id}/content` | Скачать состояние, снимок или лог |

В пакете допускается до 200 ID. Недоступный/несуществующий ID приводит к `404`
для всего запроса; пакет отменяется атомарно. Неготовый результат имеет `result=null`.

Повтор создания с тем же `Idempotency-Key` и тем же телом возвращает тот же объект,
включая его актуальный статус. Другое тело с прежним ключом даёт `409`. Ключи
привязаны к владельцу и операции; пока они сохраняются вместе с историей без TTL.

## Отмена и отказы

Основной путь команды: `queued → dispatched → running → completed`.
`dispatched` означает сохранённое назначение; `running` появляется после сообщения
агента о запуске. Ненулевой код Pytest — `completed`, `success=false`.

Терминальные состояния: `completed`, `cancelled`, `timed_out`, `isolate_failed`,
`failed` (например, агент не смог запустить процесс). Для каждого из них результат
сохраняется в той же транзакции, что и статус. При отсутствии известного кода выхода
`returncode=null`.

Внешняя отмена невыданной команды сразу даёт `cancelled`. Если задание хотя бы раз
доставлялось, сервер сохраняет `cancel_requested` и отдельную задачу `cancel` для
агента. Только подтверждение остановки позволяет вернуть `cancelled` или
`timed_out`. Если обычное завершение подтверждено раньше остановки, сохраняется его
результат. Повтор отмены безопасен, терминальный результат не перезаписывается.

Будущий демон отмены плагина может хранить пары `(command_id, cantok_token)` и
отправлять ID отменённых токенов пакетами в `/commands/cancel`. Демон результатов
продолжает ожидать терминальный статус и затем будит поток `run()`. Получение
`202 cancel_requested` ещё не означает, что процесс прерван.

Если агент сам остановил процесс по локальному таймауту, он сообщает
`outcome=timed_out` в завершении `run`, сохраняя код и логи сразу, без ожидания тика
контроллера. Для служебных задач разрешены только `completed` и `failed`.

Исчезновение воркера фиксируется по истечении lease. Команды завершаются
`isolate_failed`, а ёмкость компьютера остаётся зарезервированной до подтверждённой
очистки. API не может физически остановить отключённый компьютер: локальную
остановку по lease должен обеспечивать агент. Произвольные команды автоматически
не перезапускаются. Гарантии ровно одного физического запуска при любом сбое нет.

## Архитектура и конфигурация

- `accounts.py`, `computers.py`: учётные сущности и доступ.
- `jobs.py`, `artifacts.py`: клиентский API выполнения и файлов.
- `agents.py`: отдельный протокол агентов `/agent/v1`.
- `execution.py`: переходы состояний и распределение ресурсов.
- `resources.py`, `resource_ledger.py`, `resource_history.py`: ресурсы, журнал изменений и отчёты.
- `controller.py`: периодическая обработка сохранённых записей.
- `models.py`, `migrations/`: схема и миграции БД.

Каждая изменяющая транзакция сначала блокирует единственную координационную строку
БД. Это намеренное ограничение небольшой первой версии: оно предотвращает
перерасход ресурсов и гонки статусов также при нескольких процессах API. Сетевое
ожидание long polling и загрузка файлов происходят вне этой транзакции. После
роста нагрузки блокировку можно заменить более локальными блокировками.

SQLite использует WAL, внешние ключи и `busy_timeout`. Держите базу на локальном
диске. Сервер и контроллер должны видеть одно файловое хранилище. Брокер сообщений
не требуется. Отдельные endpoint-пространства `/admin` и `/` оставлены для будущих
интерфейсов.

Все настройки имеют префикс `THRONG_`; полный список — в `throng_api/config.py`.
Основные значения по умолчанию:

| Настройка | Значение |
|---|---:|
| `CONTROLLER_INTERVAL` | 1 секунда |
| `AGENT_LEASE_SECONDS` | 60 секунд |
| `ISOLATE_TTL_SECONDS` | 3600 секунд |
| `PROVISIONING_TIMEOUT_SECONDS` | 300 секунд, включая ожидание свободного компьютера |
| `TASK_ACK_TIMEOUT_SECONDS` | 60 секунд до запуска команды |
| `CANCELLATION_TIMEOUT_SECONDS` | 30 секунд |
| `COMMAND_QUEUE_TIMEOUT_SECONDS` | 3600 секунд |
| `MAX_OWNER_ISOLATES` | 10 активных изолятов |
| `MAX_PENDING_COMMANDS_PER_ISOLATE` | 1000 |
| `MAX_ARTIFACT_BYTES` | 100 MiB |
| `MAX_OWNER_STORAGE_BYTES` | 1 GiB |
| `ALLOW_REGISTRATION` | `true` |

Архивы хранятся как непрозрачные байты, сервер их не распаковывает. Файлы
состояния и логи, на которые ссылается история, защищены от удаления внешними
ключами. Автоматическая очистка истории и файлов-сирот после аварийного завершения
загрузки пока не реализована; учитывайте их при обслуживании и резервном копировании.
Для больших stdout/stderr предусмотрены отдельные артефакты; inline-поля ограничены
1 048 576 символами каждое.

Для PostgreSQL предусмотрен драйвер `asyncpg` и переносимая схема:

```sh
THRONG_DATABASE_URL='postgresql+asyncpg://user:password@localhost/throng' uv run throng-api migrate
```

Это создаёт схему в целевой БД. Перенос существующих данных SQLite требует отдельной
процедуры; смена URL сама по себе данные не переносит.

## GitHub Actions

API поддерживает подключение GitHub App, привязки workflow к личным и
организационным Power Cells и одноразовые JIT runners. Нет свободного Mac —
немедленная ошибка routing, без резервного запуска на GitHub.
Конфигурация, endpoints, модель доступа, генерация workflow и ограничения
описаны в [GitHub Actions](docs/github.md). Перед публичным использованием
требуются серверные credentials и проверка настоящего job: локальные HTTP-тесты
не подтверждают исполнение GitHub workflow внутри VM.

## Проверки

```sh
uv run pytest -q
uv run pytest -q --cov=throng_api --cov-report=term-missing --cov-report=html
uv run ruff check .
uv run ruff check tests --select D103
uv run ruff format --check .
uv build
```

В `../../tests/platform/api/e2e/` API запускается через Uvicorn на настоящем TCP-сокете с фоновым
контроллером, временной БД и файловым хранилищем. Тесты посылают прямые HTTP-запросы
от клиента и будущего агента: CRUD, роли и токены, исполнение, отмена, таймауты,
повторная доставка, snapshot, квоты, обрыв загрузки, смена сессий, остановка API
и одновременная работа двух контроллеров. Отдельный процесс проверяет запуск CLI.
Фактическое исполнение команд и изоляция на компьютере остаются задачей будущего агента.

В `../../tests/platform/api/e2e/auth/` каждый защищённый HTTP-метод проверяется с отсутствующими,
невалидными и неподходящими credentials. Для клиентских ручек дополнительно
проверяются истечение и отзыв токена и отсутствие нужного scope, для агентских —
ротация credential и отсутствие, истечение и смена сессии. Матрица запросов
сверяется с полным списком методов OpenAPI: новая ручка требует явного добавления
в проверки либо в список публичных методов. Проверки отправляют валидные тела и ID
существующих ресурсов, чтобы ошибки валидации не маскировали отсутствие защиты.
Авторизация выполнения дополнительно проверяется для чужих изолятов, всех ролей
членства, удаления членства, повторов запросов, подмены владельца и компьютера,
а также выбора пула при наличии свободных чужих компьютеров.

В `../../tests/platform/api/e2e/resources/` проверяются каталог и системная роль, CRUD ресурсов,
совместимость старых полей, сводки и временные границы истории, смена владельца,
удаление, пагинация, конкурирующие обновления и освобождение резервов.
Интеграционные проверки обходят HTTP для проверки ограничений БД, вызывают сбой
записи истории и обновляют старую БД с уже занятыми ресурсами и выполняемой работой.
Дополнительно проверяются передача компьютера во время чтения списка и истории,
постоянное число запросов описаний типов на страницу и загрузка только последнего
снимка каждого ресурса для начального состояния графика.
Проверки остановки сервера подтверждают завершение текущей транзакции контроллера
и возможность выполнить миграцию ресурсов сразу после закрытия соединений.

`../../tests/platform/api/integration/` дополняет эти сценарии проверками миграций, ограничений БД,
хранения секретов и искусственно вызванных сбоев COMMIT и контроллера. Все основные
ресурсы создаются фикстурами в `conftest.py`; обёрток над HTTP-запросами нет.
Каждый тест имеет докстринг; CI проверяет это правилом Ruff `D103`.
Управляемые часы позволяют проверять длительные сроки
без ожидания в реальном времени; основной e2e-набор не вызывает контроллер вручную.

CI требует 100% суммарного покрытия строк и ветвлений.
Для SQLAlchemy включён учёт `greenlet`, для CLI — учёт отдельного процесса;
HTML-отчёт сохраняется в `htmlcov/`.
Дополнительные проверки закрывают обрыв long polling, одновременные таймауты очистки,
передачу архивированных ресурсов и гонки удаления владельца/издателя токена и смены
его роли. Внутренние переходы проверяются на повторное завершение и освобождение
резервов; неизвестный тип задания должен отклоняться без изменения состояния.
Регрессии общего ревью проверяют передачу компьютера во время чтения списка,
удаление пользователя или компьютера во время аутентификации, единый снимок статуса
и результата команды, постоянное число запросов пакетного опроса, границы входных
данных и загрузку, пересекающую дедлайн задачи. Смена пароля проверяется на отказ
до дорогостоящего хэширования и повторную проверку токена перед сохранением.
CI содержит отдельную проверку PostgreSQL. Для её локального запуска можно задать
`THRONG_TEST_POSTGRES_ADMIN_URL`: тесты создают и удаляют собственные базы с именами
`throng_test_<random>`, не меняя таблицы существующей базы.

Проверки изоляции реального кода станут частью реализации агента. Для общего пула
недоверенных владельцев дополнительно потребуются правила предоставления ресурсов,
выбор sandbox runtime и модель доверия к результатам: владелец компьютера имеет
доступ к исполняемому коду и способен подменить результат.

## Power Cell

Сервер поддерживает регистрацию Mac через Apple Managed Device Attestation/ACME,
подписанные запросы устройства, динамические лимиты, вытеснение, отвязку и поздние
диагностические отчёты. Настройка центра выдачи сертификатов и полный контракт:
[docs/powercell.md](docs/powercell.md). Перед обновлением примените миграцию `0006`.
Без настроенного HTTPS ACME и ключа CA регистрация Power Cell отключена;
существующие универсальные агенты продолжают использовать прежний протокол.

## Прямой доступ из личного кабинета

Браузер на `https://platform.mutating.tech` обращается напрямую к этому API
по адресу `https://api.mutating.tech/v1`. Сервер кабинета не пересылает запросы.
`POST /v1/auth/session` принимает те же login/password, что `/v1/auth/login`,
возвращает профиль пользователя и выдаёт host-only HttpOnly-cookie `tmc_session`
с Path=/v1/, SameSite=Lax и Secure. GET читает профиль, DELETE отзывает токен.
Программные клиенты продолжают использовать `/v1/auth/login` и bearer-токены.

Оба способа используют существующую таблицу AccessToken с хэшами случайных
токенов. JWT и отдельной таблицы веб-сессий нет. Удаление/отзыв токена немедленно
прекращает доступ и через cookie. Права проверяются по актуальным данным БД.
Ответ `401` не изменяет cookie: запоздалый отказ старого запроса не должен удалить
cookie более нового входа. Cookie удаляют явный выход и удаление аккаунта.

`THRONG_BROWSER_ORIGINS` — JSON-массив точных разрешённых origin; production
по умолчанию `["https://platform.mutating.tech"]`. CORS разрешает credentials и
предоставляет браузеру X-Total-Count для пагинации. Изменяющие запросы с cookie
и POST/DELETE сессии требуют разрешённый Origin и заголовок
`X-Requested-With: ThrongDashboard`. Для локального HTTP настройте origins
явно и задайте `THRONG_BROWSER_SECURE_COOKIE=false`.
