# Компьютерные ресурсы

Все пути ниже начинаются с `/v1`. Нужен `Authorization: Bearer <access_token>`.
Чтение требует scope `read`, изменение — `manage`; scope дополнительно ограничен
правами владельца и ролью в компании. Чужие и отсутствующие объекты возвращают
одинаковый `404`, чтобы не раскрывать существование чужих ресурсов.

## Модель и единицы

`ResourceType`: UUID `id`, `name`, `description`, уникальный `code`, `unit`, `builtin`.
Миграция создаёт два встроенных типа:

| ID | code | unit | Значение |
|---|---|---|---|
| `00000000-0000-0000-0000-000000000001` | `cpu` | `millicore` | 1000 = одно логическое ядро |
| `00000000-0000-0000-0000-000000000002` | `memory` | `byte` | Объём памяти в байтах |

`ComputerResource`: UUID `id`, `computer_id`, `resource_type_id`, `total`, `occupied`,
`version`, `created_at`. Ответ также содержит `free` и вложенное описание
`resource_type`, чтобы обычному пользователю не требовался доступ к каталогу.

`total` — мощность, предоставленная сервису, `occupied` — резерв под изоляты,
`free = total - occupied`. Значения целые, без округления; `0 ≤ occupied ≤ total ≤ 2^60`.
CPU может быть дробным в ядрах: `1500 millicores = 1.5 ядра`. Уникальность пары
`(computer_id, resource_type_id)` и ограничения количества закреплены в БД.

`occupied` изменяет только контроллер/протокол исполнения. Успешное завершение или
отмена команды не уничтожает её изолят и не освобождает резерв. Освобождение
происходит после подтверждённого уничтожения изолята или чистого старта агента.
При потере агента резерв сохраняется до подтверждения очистки.

Загрузка CPU и занятая другими программами RAM здесь не измеряются. Пользовательские
типы поддерживают CRUD, сводки и историю мощности; запросы таких ресурсов для
изолятов пока не реализованы, поэтому их `occupied` остаётся нулём. Диск продолжает
учитываться через существующие поля компьютера и изолята.

## Каталог типов и системная роль

| Методы | Путь |
|---|---|
| `GET`, `POST` | `/resource-types` |
| `GET`, `PATCH`, `DELETE` | `/resource-types/{type_id}` |

Все методы, включая чтение списка, требуют личного токена системного администратора.
Компания и её токены этой роли не имеют, в том числе когда токен выпущен системным
администратором. Компания может иметь собственных `creator`/`admin`, но это отдельные
роли. Системная роль проверяется на каждом запросе, а не запоминается в токене.

После регистрации пользователя оператор сервера выполняет:

```sh
uv run throng-api system-admin <user-uuid>
uv run throng-api system-admin <user-uuid> --revoke
```

Регистрация и изменение профиля не принимают поле `is_system_admin`. Роль отображается
в собственном профиле. Она даёт только управление каталогом, не доступ к чужим данным.

Создание типа:

```json
{"name":"GPU","description":"Количество ускорителей","code":"gpu","unit":"device"}
```

`PATCH` меняет `name` и `description`. Код и единица неизменяемы, чтобы история
не смешивала разные измерения. Встроенные типы нельзя удалить (`409`). Тип с активными
ресурсами также нельзя удалить. Остальные архивируются; старые записи истории
сохраняют связь с типом, его код остаётся занят. Названия в отчётах берутся из
актуального описания типа.

## CRUD ресурсов компьютера

| Методы | Путь | Права |
|---|---|---|
| `GET` | `/computers/{computer_id}/resources` | Владелец или член компании |
| `POST` | `/computers/{computer_id}/resources` | Владелец или creator/admin компании |
| `GET` | `/computer-resources/{resource_id}` | Владелец или член компании |
| `PATCH`, `DELETE` | `/computer-resources/{resource_id}` | Владелец или creator/admin компании |

Коллекции используют `limit` (1–200, по умолчанию 100) и `offset`.
Новый компьютер автоматически получает CPU и Memory из существующих полей запроса.
Для дополнительного ресурса:

```json
{"resource_type_id":"<uuid типа>","total":4}
```

Повторное создание активной пары компьютер/тип возвращает `409`.
Изменение мощности с защитой от потери параллельного изменения:

```json
{"total":8,"expected_version":1}
```

`expected_version` необязателен; несовпадение даёт `409`. Реальное изменение увеличивает
`version`; повтор того же значения не создаёт новую версию или историческое событие.
Уменьшение ниже `occupied` и удаление занятого ресурса возвращают `409`.

Удаление архивирует запись и обнуляет её вклад в сводки. Повторный `POST` с тем же
типом восстанавливает тот же UUID с новой версией. Неиспользуемые CPU/Memory тоже
можно удалить; компьютер без одного из них не получает новые изоляты.
`PATCH /computers/{id}` со старым полем мощности может восстановить встроенный ресурс.
Дублирующих счётчиков CPU/Memory в таблице компьютеров нет.

## Сводки

`GET /users/{user_id}/resources/summary` — собственные личные компьютеры пользователя.
`GET /companies/{company_id}/resources/summary` — компьютеры компании, доступно её
членам и корпоративному токену. Личные компьютеры сотрудников не входят в сумму компании.
Системная роль не отменяет эти ограничения.

Ответ содержит `as_of`, `only_available`, `computer_count` и массив `resources` с полями
`resource_type_id`, `name`, `code`, `unit`, `total`, `occupied`, `free`.
Суммирование производится отдельно для каждого типа; отсутствующие типы не включаются.

По умолчанию учитывается всё неархивное имущество владельца, включая отключённые
компьютеры и компьютеры без связи. `?only_available=true` оставляет только компьютеры
с `enabled=true`, `online=true`, активной сессией и ещё действующим lease. Это свободная ёмкость
по данным сервера; агент должен проверять фактическую возможность запуска на машине.

## История для графиков

| Путь | Область |
|---|---|
| `/users/{user_id}/resources/history` | Личный пул |
| `/companies/{company_id}/resources/history` | Пул компании |
| `/computer-resources/{resource_id}/history` | Один ресурс текущего компьютера |

Параметры:

- `from`, `to`: обязательные ISO 8601 с часовым поясом, `from < to`;
- `resource_type_id`: необязательный фильтр для отчёта пользователя/компании;
- `limit`: число транзакционных точек, 1–2000, по умолчанию 500;
- `snapshot_revision`, `after_revision`: продолжение пагинации.

Например: `?from=2026-10-01T00:00:00Z&to=2026-10-02T00:00:00Z`.
Отчёт относится ко всему имуществу; фильтр `only_available` в истории не применяется.

Ответ содержит:

- `from_time`, `to_time`: границы в UTC;
- `available_from`: дата исходного снимка миграции для старой БД, иначе `null`;
- `initial_at`, `initial`: начальное состояние графика;
- `points`: точки `{at, revision, resources}` с полным состоянием сумм после изменения;
- `snapshot_revision`: фиксированная ревизия отчёта;
- `next_after_revision`: курсор следующей страницы либо `null`.

Интервал — `[from,to)`. Изменения ровно в `from` включаются в `initial`, изменения
ровно в `to` не включаются. Если есть миграционный снимок позднее `from`, начало
сдвигается к `available_from`: историю до внедрения журнала восстановить нельзя.
Интервал полностью до снимка имеет `initial_at=null`, пустые `initial` и `points`.

Для следующей страницы повторите границы и фильтр, передайте `snapshot_revision`
первого ответа и `after_revision=next_after_revision` предыдущего. Новые записи
после снимка не попадут в оставшиеся страницы. `initial` следующей страницы — состояние
после предыдущей; не нужно складывать его со значениями предыдущих точек.
Одна транзакция резервирования CPU/Memory даёт одну точку; пагинация не разбивает
её на части. Разные транзакции с одинаковым временем различаются `revision`.
Для ступенчатого графика используйте этот порядок и продолжите последнюю точку до `to`.

Журнал хранит значения до и после изменения, исторических владельцев, версию,
ревизию, время и причину. Изменение мощности и запись журнала коммитятся вместе.
Передача компьютера вычитает мощности у прежнего владельца и добавляет новому,
не переписывая старые события. Новый владелец видит историю только своего владения;
ответ не раскрывает идентификаторы прежних владельцев. После отзыва членства
история компании также становится недоступна.

Архивированный ресурс доступен через свою ручку истории, пока существует компьютер
и запрашивающий имеет доступ к его текущему владельцу. После удаления компьютера
история сохраняется в отчётах соответствующего пользователя/компании. Удаление
компьютера с историей исполнения, как и раньше, ограничено внешними ключами.

## История доступных мощностей для кабинета

`GET /users/{user_id}/resources/availability-history` и
`GET /companies/{company_id}/resources/availability-history` имеют те же ограничения
доступа, что и сводки соответствующего владельца. Принимают обязательные `from`, `to`
с часовым поясом, `from < to`, интервал не более 31 дня. Будущее обрезается по `as_of`.

Ответ: `from_time`, `to_time`, `as_of`, `available_from`, `points`. Каждая точка
содержит `at`, `cpu_millis`, `memory_bytes`, `cpu_occupied_millis`,
`memory_occupied_bytes`. Последняя точка продлевает состояние до конца известного
интервала; нулевые по длительности изменения пропускаются. Эти данные подходят для
одного ступенчатого графика выделенной мощности и резервов задач.

В суммы входят только включённые компьютеры онлайн с действующими сессией и lease.
Истечение lease завершает вклад компьютера независимо от задержки контроллера.
Изменения мощности, резервов, состояния связи и владельца сохраняются в той же
транзакции. История относится к владельцу в момент события, без раскрытия прежних
владельцев; удаление или передача компьютера не переписывает прошлое.

`available_from` — время миграции `0005`. Она создаёт исходные интервалы для уже
подключённых компьютеров. До этой даты нет измерений, а не нулевая мощность.
Это отдельный отчёт от `/resources/history`, который описывает всё имущество
владельца независимо от доступности. Динамические лимиты и телеметрия будущего
агента, а также реакция планировщика на их изменения здесь не реализуются.
