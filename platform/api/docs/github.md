# GitHub Actions

Реализация включает OAuth GitHub App, зашифрованные пользовательские токены
с обновлением, установки/репозитории, привязки workflow к пулам Power Cells,
OIDC-резервирование, JIT runner lifecycle и подписанные webhooks.

Основной CI выполняется только на Power Cells. Нет подходящего свободного Mac —
немедленный отказ без очереди и без VM. Для выделенного Mac остаётся ограниченный
срок подготовки VM/образа/runner. Ошибки API или подготовки завершают routing
и workflow с failure; зависимый job пропускается. Вспомогательный routing job
по-прежнему hosted, ему нужны доступные минуты GitHub. OAuth callbacks сохранены.

Credentials и API/кабинет развёрнуты через Ansible. Утверждения, границы моков,
команды запуска и реальные проверки описаны в
[проверках интеграции](../../../docs/github-actions-testing.md).

## Настройка

Параметры `THRONG_GITHUB_*` описаны в `.env.example` и
[инструкции подготовки](../../../docs/github-actions-dev-setup.md). Частичная
конфигурация отклоняется при старте. Без credentials `/v1/github/status`
возвращает `enabled: false`, и навигационная вкладка Actions скрыта.

Для миграции используйте `throng-api migrate`: revision `0010` добавляет
GitHub/CI таблицы, `0011` удаляет поля fallback и переводит исторические отказы
размещения на Power Cell в `failed`, сохраняя причины, ссылки и состояние очистки.
`0012` завершает прежние CI-очереди без выделенного Mac, сохраняя историю
и состояние очистки. Общий планировщик больше не подбирает Mac повторно для CI.
`0013` сохраняет подтверждённый момент запуска job: guard помнит его после выхода
runner, перезапуска API и временной недоступности результата GitHub. При обновлении
заполняются только записи `running`; для неоднозначной истории старт не угадывается.
Применяйте миграции перед запуском нового API. Сохраняйте постоянный Fernet key
вместе с резервными копиями БД. Секреты App не хранятся в БД.


## Подключение аккаунта

Все операции, кроме callbacks, CI routing и webhook, используют обычный
AccessToken/BrowserSession платформы. Изменения требуют `manage`, подключение —
личного токена. Cookie-запросы сохраняют существующую проверку Origin/CSRF.

| Метод | URL относительно `/v1/github` | Назначение |
| --- | --- | --- |
| GET | `/status` | Доступность интеграции, ID/login подключённого GitHub пользователя |
| POST | `/authorize` | GitHub OAuth URL с одноразовым state текущей сессии |
| GET | `/oauth/callback` | Обмен code, проверка GitHub identity и возврат в `/actions` |
| POST | `/installations/authorize` | Установка App с state текущей сессии |
| GET | `/installations/callback` | Возврат после установки; без state ничего не привязывает |
| GET | `/installations?page=1` | Установки этого App, доступные подключённому пользователю |
| GET | `/installations/{id}/repositories?page=1` | Репозитории установки, доступные пользователю |
| DELETE | `/connection` | Удаление credentials и state, отключение созданных пользователем CI-привязок |

OAuth state действует 10 минут, хранится как SHA-256 и связан с пользователем,
назначением и токеном инициирующей сессии. Обмен не держит блокировку БД, затем
повторно проверяет сессию. Refresh сериализован отдельным lease. Обе страницы
GitHub списков используют по 100 элементов. Disconnect не удаляет установку App
из GitHub; новые назначения прекращаются, контроллер очищает активные runners.

## Привязка

`POST /v1/github/routes` требует `manage` и `execute`, личного пользователя,
GitHub repository admin и доступа App именно к указанному repository ID. Для
организации платформы дополнительно нужны `resources.manage` и `execution.run`.
Эти права и связь GitHub проверяются снова перед назначением.

```json
{
  "installation_id": 172111136,
  "repository_id": 1422262495,
  "workflow_path": ".github/workflows/ci.yml",
  "job_key": "test",
  "ref": "refs/heads/main",
  "company_id": null,
  "computer_ids": [],
  "cpu_millis": 2000,
  "memory_bytes": 4294967296,
  "disk_bytes": 10737418240,
  "preparation_seconds": 90,
  "timeout_seconds": 3600,
  "max_parallel": 1
}
```

Пустой `computer_ids` означает весь выбранный пул; непустой список ограничивает
назначение перечисленными компьютерами. Проверяются их принадлежность пулу и
runtime Power Cell. Ресурсы одного job выделяются на одном Mac; минимальная RAM —
16 MiB, максимальный диск — 1 TiB, как в контракте агента. Для каждого
запуска используется пустое начальное состояние, образ `actions`, режим `vm` и
запрет автоматического повторного исполнения после потери изолята.
Срок подготовки выделенного Mac `preparation_seconds` допускает 10–300 секунд (по умолчанию
90). Холодная загрузка официального образа может потребовать 300 секунд;
это время не увеличивает CPU/RAM job. Генератор даёт routing job дополнительную
минуту сверх ожидания, минимум четыре минуты. Bootstrap обновляет OIDC identity
каждые 120 секунд, не меняя исходный deadline.
Изолятом и командами CI управляет Actions: обычный execution API возвращает 409
для ручных commands, snapshots, renew, destroy и cancel таких ресурсов, в том
числе для участников корпоративного пула. Метаданные доступны согласно правам чтения.

`GET /routes` — список доступных привязок, `limit` до 200 и `offset`.
При создании `ref` должен быть допустимым Git ref в формате `refs/heads/...`:
компоненты не начинаются с точки и не заканчиваются на `.lock`, весь ref не
заканчивается точкой или слешем. Неверные значения дают 422 до обращения к GitHub.
`GET /routes/{id}/workflow` выдаёт самостоятельный пример YAML с Python bootstrap
из поставки API. Его routing job должен быть добавлен в workflow, а основной
job получает `needs` и матрицу с двумя ролями: `workload` на Power Cell и
`queue_guard` на hosted ARM64. `strategy.fail-fast: true`, `max-parallel: 2` и
`continue-on-error: false` обязательны. Каждый исходный CI step получает условие
`if: matrix.role == 'workload'`; существующий `if` сохраняется через `&&`.
Исходный CI на guard не выполняется. Permissions и зависимости сохраняет автор
workflow; основной job получает `id-token: write` для observer leg, без
`actions: write`. Пример рассчитан на один job, а не на автоматическую обёртку
существующей пользовательской матрицы. Имена checks: `<job> (workload)` и
`<job> (queue guard)`; обновите branch protection. Скопируйте все исходные upstream `needs`
основного job также в routing job: выбор runner должен идти после upstream jobs.
Согласования environment и ожидания job-level concurrency после routing пока
не поддерживаются: runner ждёт назначения только пять минут. Такие барьеры нужно
завершать до routing. Каждый пример имеет уникальный routing job ID, поэтому
разные привязки jobs одного workflow не конфликтуют. `job_key` — имя job для
генерируемого примера; OIDC авторизует workflow целиком, а не отдельный job:
GitHub OIDC не содержит надёжного job ID для этой проверки. В доверенную границу пула входят авторы всех jobs данного репозитория, включая
допущенные к выполнению PR. GitHub регистрирует JIT runner на репозиторий и
назначает jobs по меткам, без привязки к нашему OIDC run/ref. Уникальная метка —
идентификатор, а не секрет или правило доступа. Проверка OIDC ограничивает
резервирование через платформу; она не даёт гарантии изоляции от других jobs
того же репозитория. Подключать репозиторий с недоверенными исполняемыми workflows
к доверенному пулу нельзя считать безопасным только из-за этих проверок.

Частичный GitHub rerun может повторно использовать outputs успешного routing job.
Пример сверяет `run_attempt`: при несовпадении останавливается на вычислении
`runs-on` до назначения машины. Чтобы
снова выбрать Power Cell, повторите routing job вместе с зависимыми jobs либо
используйте **Re-run all jobs**. При переносе примера сохраните проверку attempt
и соответствующий routing output. В защите ветки требуйте routing check
(`powercell_route_<id>`) и checks `<job> (workload)` / `<job> (queue guard)`:
пропущенный зависимый job сам по себе не гарантирует запрет merge.

`DELETE /routes/{id}` отключает привязку, оставляя историю.
`GET /routes/{id}/runs?limit=50` возвращает статусы, причины выбора, isolate ID и
ссылки на GitHub. Credentials и внутренняя controller lease в ответ не входят.
Изменение параметров, rename или transfer репозитория требует новой привязки
и отключения старой: OIDC закреплён за исходным именем/owner/ref. Очистка старых
запусков разрешает каноническое имя по постоянному repository ID и не зависит
от redirect со старого имени.

## Выбор runner и очистка

Bootstrap работает на GitHub-hosted ARM64 и получает короткий OIDC token с
`aud = <public API origin>/v1/github/ci`. Запрос:

```text
POST /v1/github/ci/routes/{id}/reserve
Authorization: Bearer <GitHub OIDC token>
{"instance":"default"}
```

`reserve?wait_seconds=20` может ожидать смену `preparing` до 20 секунд.
Без параметра ответ немедленный, как у прежних клиентов. Ожидание использует
короткие чтения БД без удержания транзакции и не вызывает GitHub API;
готовое решение и отказ `no_capacity` возвращаются сразу. Bootstrap из нового примера workflow
использует это ожидание с HTTP timeout на пять секунд больше, ограничивая его
оставшимся общим сроком. Обновление существующего workflow обязательно:
замените весь встроенный routing script и outputs из сгенерированного примера.
Старый script содержит самостоятельный переход на GitHub при сетевой ошибке;
одного обновления API недостаточно. Прежние поля `fallback` в запросах создания
привязок теперь отклоняются с 422.

В первые десять секунд после создания JIT-команды контроллер проверяет
готовность чаще: раз в 1–5 секунд с учётом числа неочищенных резерваций той же
установки App. Затем возвращается прежний интервал 5 секунд. Частота проверок
работающих jobs, backoff ошибок, авторизация и ресурсные лимиты не меняются.

Все запросы одной проверки используют общий HTTPS keep-alive; соединения
закрываются после проверки, в том числе при ошибке или отмене. Полномочия
по-прежнему проверяются заново, временные токены отзываются, cookies не сохраняются.

Проверяются RS256, фиксированные issuer/JWKS, audience, время, repository/owner
IDs, workflow path/ref, событие и GitHub-hosted источник. Сейчас Power Cells
разрешены для `push` и `workflow_dispatch` указанной ветки. Pull requests и
остальные события завершаются ошибкой routing; `pull_request_target` не
может резервировать пул через OIDC API. Это ограничение reserve, а не отдельное
правило GitHub assignment для репозиторного runner. Reusable workflows требуют отдельного расширения политики.

Ключ идемпотентности: route + run ID + run attempt + instance. Для матрицы нужен
отдельный bootstrap на каждый instance с устойчивым уникальным
`POWERCELL_INSTANCE`; обычный пример генерируется для одного job. Повтор запроса
не создаёт новую VM; новый attempt получает отдельную резервацию.

В одной write-транзакции общий планировщик выбирает Mac и резервирует CPU/RAM/disk.
Только после выделения возвращается `status: preparing`. Если свободных ресурсов
нет, сразу возвращается `status: failed, reason: no_capacity` без изолята или
задачи агенту. Повтор запроса возвращает тот же отказ: появление Mac позже не
возобновляет отклонённый attempt. После подготовки изолята контроллер повторно
проверяет GitHub доступ и workflow run, регистрирует одноразовый JIT runner,
запускает официальный `run.sh` и ждёт `online` плюс подтверждения запуска агентом.
Тогда результат содержит `runs_on: ["powercell-<uuid>"]`.

Перед выдачей готовой метки сам `reserve` в write-транзакции повторно проверяет
права создателя, сроки, VM, команду runner и сессию назначенного Mac. Это действует
для готового ответа сразу и после long polling. Только после проверки выполняется
`ready → selected` и возвращается `runs_on`; отдельного `/commit` нет.
До выдачи готовности действует исходный срок подготовки. После выдачи runner имеет
не более пяти минут на получение job; повтор запроса этот срок не продлевает.
Начало job меняет срок на его timeout. Сроки также отражаются в lifetime изолята,
поэтому общий scheduler может очистить его независимо от CI controller.

После обновления API замените встроенный bootstrap новым примером: прежний script
вызывал удалённый endpoint `/commit`. `cancel` и cancellation tombstone сохранены.

Если bootstrap завершается ошибкой после потери связи или истечения срока, он
вызывает `POST /ci/routes/{id}/cancel`. Отмена создаёт идемпотентную запись даже
если исходный reserve ещё проверяет GitHub: поздний запрос увидит отмену и не
создаст VM. Начавшийся job отменять этим endpoint нельзя. Недоступный cancel
страхуется сроком подготовки и lease выбранного runner. Долгоживущего
персонального токена платформы в workflow нет.

`POST /ci/routes/{id}/watch` принимает тот же OIDC и `{"instance":"default"}`.
Он только читает резервацию с точным route/run/attempt/instance: не создаёт
резерваций, изолятов, задач и не меняет сроки или selection. Ответы:
`{"status":"waiting"}`, `{"status":"started"}` либо
`{"status":"failed","reason":"runner_timeout"}`. Подтверждённый старт или
авторитетный результат GitHub завершают guard успешно; истечение lease, потеря
runner, отзыв доступа или отсутствующая резервация завершают его ошибкой.
Неопределённый `runner_exited` ожидает уточнения результата до истечения срока.

Сгенерированный hosted guard опрашивает `watch` каждые две секунды, обновляет
OIDC каждые 120 секунд и ограничен 310 секундами независимо от preparation.
Краткие HTTP 429/5xx и транспортные ошибки повторяются в этом бюджете с учётом
числового `Retry-After`, ограниченного остатком срока. При временном отказе
обновления OIDC ранее выданный токен продолжает наблюдение, пока API принимает
его; повтор обновления соблюдает отдельный cooldown issuer. Другие HTTP ошибки,
некорректный JSON или неизвестные состояния немедленно завершают guard ошибкой.
Observer не публикует `runs_on`, не вызывает reserve/cancel и
не продлевает lease. POSIX alarm прерывает даже непрерывное медленное чтение HTTP
через 310 секунд и завершает процесс обычной ошибкой. Его отдельный job timeout —
шесть минут: сам по себе он даёт `cancelled` и не запускает matrix fail-fast. Timeout workload
сохраняет `timeout_seconds` привязки. Через нативный `strategy.fail-fast` GitHub
отменяет queued/in-progress workload этой матрицы текущего attempt без REST
отмены всего run и без новых App permissions. Остальные jobs и новые attempts
не затрагиваются. Гарантия зависит от доступности hosted guard и планировщика
GitHub: обычный job timeout сам по себе не ограничивает очередь self-hosted
runner, которая у GitHub может ожидать до 24 часов.

При истечении подготовки, квотах или ошибке GitHub возвращается `status: failed`
и машинная причина, без `runs_on`. Bootstrap завершается с ненулевым exit code;
routing job и workflow имеют результат failure, зависимый основной job пропущен.
При сетевой ошибке или недоступности OIDC/API результат также failure; output
исполнителя не публикуется. Перехода на другого исполнителя нет, ограничений
стандартного GitHub runner на ресурсы привязки больше нет.

Routing job и queue guard выполняются на GitHub-hosted ARM64:
им нужны доступные hosted минуты и отсутствие billing-блокировок. Routing позволяет
сообщить GitHub явную ошибку, когда своих Mac нет; основной CI выполняется на Mac.

JIT-конфигурация зашифрована в резервации; обычные Command.env и AgentTask.payload
её не содержат. Расшифровка происходит при выдаче задачи только назначенному
аутентифицированному агенту; локальный журнал агента исключает JIT при сериализации.
После завершения/отмены секрет удаляется, изолят
уничтожается, runner удаляется из GitHub. Занятые ресурсы освобождаются только
после подтверждения агента либо подтверждённого чистого старта. Неизвестная
регистрация после сбоя находится по уникальному имени; финальная проверка
очистки учитывает срок controller lease. Offline Mac сохраняет резервацию до
подтверждения очистки, чтобы не назначить эти ресурсы повторно.

Webhook: `POST /v1/github/webhook`, HMAC SHA-256 сырых байтов, обязательный
`X-GitHub-Delivery`, лимит 2 MiB. ID доставки дедуплицируется, изменение payload
под тем же ID отклоняется. `workflow_job` сверяет run attempt, runner ID/name;
запоздалый in_progress не возвращает завершённую резервацию в работу.
`workflow_run` завершает оставшиеся ресурсы; удаление/приостановка установки и
удаление репозитория из App отключают привязки. Неполученные события дополнительно
страхуются опросом GitHub и сроком жизни резервации.
Обязательное событие `github_app_authorization.revoked` удаляет локальное
подключение пользователя и незавершённые OAuth exchanges, отключает его привязки.
Подготавливаемые запуски завершаются ошибкой, выбранные и выполняющиеся отменяются;
очистка использует отдельные полномочия установки App.
Точный `workflow_job.completed` имеет приоритет над общим результатом workflow,
в том числе после очистки: для сопоставления сохраняется исторический runner ID.
Если completion webhook потерян, до завершения очистки контроллер запрашивает
страницы jobs исходного workflow attempt и сверяет runner ID и имя. Повторное
уточнение результата сохраняет исходное время завершения и срок очистки.
Это уточняет только результат GitHub; отмены и таймауты платформы не заменяются,
ресурсы и polling завершённой очистки не возобновляются.
История возвращает `failed` при отказе подготовки. Причина `bootstrap_cancelled`
означает отмену подготовки; результаты действительно выполненного Power Cell job
сохраняются отдельно, включая точные success/failure/cancelled/timed_out GitHub.
Для долгих jobs, ожидания позднего результата и незавершённой очистки частота polling делит бюджет
GitHub installation между её незавершёнными резервациями. Webhooks и локальные
timeout продолжают обрабатываться сразу; переход в terminal ускоряет первую очистку.
Ответы GitHub 403/429, означающие rate limit, приостанавливают запросы общей
квоты пользователя или установки, в том числе после смены токена. Соблюдаются
`Retry-After` и исчерпанный `X-RateLimit-Reset`; без заголовков повтор начинается
не раньше минуты с увеличением задержки. API возвращает 503 с `Retry-After`,
локальные таймауты и очистка изолятов продолжаются. Обычный отказ в правах 403
не считается ограничением частоты.
GitHub инвалидирует прежний access token сразу при refresh. Если параллельный
пользовательский GET получил 401, он повторяется один раз только при наличии
изменившегося текущего токена. Неизменившийся токен и отказ при повторе сохраняют
обычную проверку полномочий; отключённое подключение не восстанавливается.

После выдачи готового self-hosted runner нет переноса уже выбранного job на
GitHub при потере Mac. Нельзя исключить исчезновение runner между ответом
bootstrap и назначением job GitHub. Официальный image не содержит весь набор
GitHub-hosted ПО; Linux ARM64, отсутствие Docker/container actions и macOS/Xcode
остаются ограничениями текущего исполнения.
