# Проверка токена для выполнения задач

`GET /v1/auth/check` — единый метод предварительной проверки личного токена
или токена организации. Тип токена определяет сервер; клиент передаёт только
`Authorization: Bearer <token>`. Тело запроса и параметры не требуются.
Как и другие клиентские методы `/v1`, метод также принимает существующую
cookie `tmc_session`. Явный заголовок Authorization имеет приоритет над cookie:
неверный bearer-токен не заменяется действующей браузерной сессией.
Пустой заголовок Authorization также приводит к `401`; действующая cookie
при ошибке явно переданного заголовка не удаляется.

Метод предназначен для настройки программного клиента и диагностики перед
загрузкой состояния или созданием изолята. В отличие от `/v1/users/me`, он
не требует личного токена и одинаково работает с обоими владельцами.

## Успешная проверка

Для `200 OK` одновременно необходимы scopes `read` и `execute`.
Scope `manage` не требуется и не заменяет ни один из них.

Для токена организации дополнительно проверяются актуальное членство издателя,
его право `tokens.manage`, необходимое для действия такого токена, и права
`execution.read` и `execution.run` именно в организации токена. Личные права
издателя или права в другой организации не компенсируют их отсутствие.
Личный токен проверяется для личного пула; отсутствие прав в организации
не мешает его использовать для собственных ресурсов.

Пример ответа для токена с минимально необходимыми scopes:

```json
{"valid": true, "scopes": ["execute", "read"]}
```

`scopes` содержит все scopes проверенного токена в лексикографическом порядке,
включая `manage`, если он выдан. Ответ не содержит секрет, его хэш или профиль
пользователя. Поле `valid` равно `true` только в успешном ответе; отказы используют
обычные HTTP-коды и объект `{"detail": "..."}`, а не `200` с `valid: false`.

## Ошибки и границы проверки

| Код | Причина |
| --- | --- |
| `401 Unauthorized` | Нет корректного Authorization/cookie; токен неизвестен, истёк, отозван или удалён; его владелец/издатель больше недействителен |
| `403 Forbidden` | Нет хотя бы одного scope `read`/`execute` либо у издателя токена организации нет нужного права выполнения |

Примеры `detail`: `Bearer token required`, `Invalid or expired token`,
`Token lacks required scope`, `Organization permission required`.
При отсутствующей или некорректной схеме аутентификации сохраняется заголовок
`WWW-Authenticate: Bearer`.

Успешные ответы и отказы `401`/`403` содержат `Cache-Control: no-store`.
Каждый вызов заново проверяет токен и текущие права. Срок действия заканчивается
точно в `expires_at`: в этот момент токен уже недействителен. Отзыв, удаление,
смена пароля и изменение членства учитываются последующими запросами без
повторного входа клиента.

Метод не создаёт изоляты, задания или артефакты, не резервирует мощности,
не продлевает токен и не требует наличия компьютеров. Успешная проверка
не гарантирует свободную ёмкость, доступность агента или сохранение прав до
следующего запроса: операции выполнения продолжают проверять авторизацию сами.
Доступ к бенчмаркам (`resources.read` для организации) проверяется отдельно
при их чтении.

## Проверки реализации

`tests/platform/api/e2e/auth/test_token_check.py` использует настоящий HTTP-сервер,
мигрированную временную БД и токены, выпущенные через API. Проверяются все семь
непустых комбинаций scopes для обоих владельцев, ошибки аутентификации, точная
граница срока, отзыв/удаление, смена пароля, текущие права издателя, приоритет
заголовка над cookie, отсутствие записи в БД, отсутствие секретов в ответе и
журнале, заголовки кеширования и контракт OpenAPI. Метод также включён в общую
матрицу авторизации всех защищённых методов.
