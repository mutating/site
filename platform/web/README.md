# Личный кабинет The Mutating Company

Отдельное приложение в том же git-репозитории: React + TypeScript в `src/`,
Python/FastAPI в `server/`, тесты в `../../tests/platform/web/`. Код кабинета не входит
в Python-пакет API. Приложение обслуживает корень `/` поддомена платформы и запускается независимо
от API и Hugo-сайта. Данные получает только через HTTP API, без доступа к его БД.

## Локальный запуск

Нужны Node.js 24, Python 3.12 и uv. Сначала запустите API из `platform/api/`:

```sh
uv sync --frozen
uv run throng-api serve
```

В другом терминале, из `platform/web/`:

```sh
npm ci
uv sync --frozen
cp .env.example .env
uv run uvicorn server.app:app --host 127.0.0.1 --port 8001
```

И в третьем терминале, также из `platform/web/`:

```sh
npm run dev
```

Открыть <http://127.0.0.1:5173/>. Vite проксирует `/api/` в Python-сервис.
Для Power Cell используйте `http://127.0.0.1:5173/v1`: Vite также проксирует
`/v1` и `/agent/v1` в API на порту 8000, сохраняя общий origin для ссылок
регистрации и кабинета. HTTPS ACME настраивается отдельно согласно `../api/docs/powercell.md`.
API должен включать миграцию `0007`; `throng-api serve` применяет её автоматически.
При использовании `localhost` вместо `127.0.0.1` измените `DASHBOARD_PUBLIC_ORIGIN`.

Для просмотра производственной сборки:

```sh
npm run build
DASHBOARD_PUBLIC_ORIGIN=http://127.0.0.1:8001 uv run uvicorn server.app:app --host 127.0.0.1 --port 8001
```

После сборки Python-сервис сам отдаёт HTML, JS, CSS, шрифты и логотип.

## Страницы и поведение

- `/`: приветствие, продукты, организации и их доступные/свободные мощности.
- `/login`, `/register`: вход по email или нику, регистрация.
  Email и пароль обязательны; имя, фамилия и ник необязательны. Подтверждения пароля,
  восстановления пароля и сторонних провайдеров нет.
- `/power-cells`: личный пул, затем пулы организаций; свободные/всего CPU и RAM,
  количество компьютеров онлайн, история за семь дней.
- `/power-cells/computers?user_id=…` или `?company_id=…`: отдельная страница
  доступных компьютеров, серверная пагинация по 10 строк с сохранением страницы в URL.
- `/cloud`: заглушка будущих облачных раннеров.
- `/profile`: ФИ, ник, аватар, удаление аккаунта и выход из сеанса.
- `/organizations`: создание, список, удаление для создателей, выход и
  входящие приглашения с принятием/отклонением.
- `/organizations/{id}`: участники с ФИ, никами, аватарами и правами;
  пагинация по 10. Менеджеры ищут пользователя по email/нику, добавляют его,
  меняют роли и отдельные разрешения, удаляют участников, создают и отзывают
  приглашения, обновляют ссылки. Настройки доступны по соответствующему праву.
- `/invitations/{token}`: просмотр и принятие приглашения. Адрес сохраняется
  при переходе через вход/регистрацию; ссылка одноразовая и имеет срок действия.

Внутренние запросы кабинета используют `/api/*`. Адреса `/account` и `/account/*`
не обслуживаются и возвращают `404` без перенаправления.
Любой закрытый маршрут перенаправляет на вход и сохраняет исходный адрес.
Создание аккаунта автоматически выполняет вход. Удаление требует ввода email/названия.
Если аккаунт уже создан, а автоматический вход временно не сработал, кабинет
переводит на вход с пояснением и заполненным email; повторная регистрация не нужна.
Серверные ограничения сохраняются: связанные ресурсы и история могут блокировать
удаление; кабинет не выполняет каскадную очистку.
Организацию с другими участниками или связями владения токенами удалить нельзя:
участники должны выйти, токены и их связи — быть явно удалены через API.
При удалении пустой организации убирается только собственное членство её создателя.

Роли задают стандартные права; для участника/администратора можно выбрать отдельные
разрешения на чтение/управление участниками, ресурсами и API-токенами, просмотр/
выполнение задач и настройки организации. Создатель всегда сохраняет полный доступ.
Менеджер участников может выдать только свои разрешения обычному участнику;
привилегированные роли назначает создатель. Потеря прав применяется API сразу.
Пулы без права чтения показывают название организации и пояснение вместо чисел.

Приглашение по email появится в кабинете получателя даже после будущей регистрации;
приглашение по нику привязывается к существующему аккаунту. Отправитель копирует
ссылку вручную; автоматическая отправка писем не настроена. Ссылка без адресата
доступна одному пользователю, который получил её. Срок — 1, 7 или 30 дней.
Обновление ссылки отключает старую, отзыв/понижение прав отправителя также блокирует
его ожидающие приглашения. Обычные списки не содержат секретов ссылок.
Нужна миграция API `0007`; `throng-api serve` применяет её при запуске.

Есть RU/EN и светлая/тёмная темы. Ключи `tmc-language` и `tmc-theme` совпадают
с основным сайтом: настройки общие при работе на одном домене. Цвета, шрифты,
форма логотипа и оформление графика перенесены из темы `mutating` основного сайта.
Глаз в шапке следит за курсором по всей странице; TMC раскрывается при наведении
в The Mutating Company, когда ширина шапки позволяет это сделать.

## Что означают ресурсы

В отчёты входят только `enabled=true`, `online=true`, действующая сессия и lease.
CPU пересчитывается из millicores в ядра, память — из байтов в GiB.
`total` — выделенная для сети мощность из API, `occupied` — резерв под изоляты,
`free = total - occupied`. Личные компьютеры сотрудников не входят в пул организации.

Один график показывает обе мощности и их занятость: четыре линии, CPU слева,
GiB справа. Сплошные линии — выделенные мощности, пунктир — резервы задач.
Линии можно скрывать; точные значения доступны в раскрывающейся таблице.
Используются ступенчатые линии без выдуманной интерполяции между событиями.

Это не физическая загрузка ОС. Передача динамических лимитов от будущего агента,
телеметрия ОС и политика остановки задач при изменении лимита в эту задачу не входят.
Кабинет показывает только реальные данные, уже известные API.
История доступности собирается с миграции `0005`: более ранний период остаётся
неизвестным и явно отмечается. Истечение lease учитывается точно, даже если
контроллер ещё не успел обработать отключение.

## Сессии и развёртывание

Python-сервис хранит API bearer-токен внутри зашифрованной HttpOnly-cookie,
`SameSite=Lax`, `Path=/api/`. В production обязательны постоянный ключ и Secure.
При переходе с прежнего префикса пользователям потребуется войти заново.
Токен не возвращается в JavaScript и не сохраняется в localStorage. При выходе
отзывается соответствующий API-токен. Срок сессии определяется API, без скрытого продления.
Изменяющие запросы проверяются по точному Origin и собственному заголовку.
Сервис пересылает только разрешённые для кабинета пути и методы.

Сгенерировать ключ:

```sh
uv run python -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'
```

Пример `/etc/throng-dashboard.env`:

```dotenv
DASHBOARD_API_URL=http://127.0.0.1:8000
DASHBOARD_PUBLIC_ORIGIN=https://platform.mutating.tech
DASHBOARD_SECURE_COOKIE=true
DASHBOARD_SESSION_KEY=<сгенерированный ключ>
```

Сохраните ключ между перезапусками и используйте одинаковый на всех экземплярах.
Локально при отсутствии ключа создаётся игнорируемый `.runtime/session.key`.

Основной production-деплой теперь использует `platform.mutating.tech` и единый
сервис systemd вместе с API. Сборка интерфейса выполняется в CI; Docker и Docker
Compose для этого не требуются. Настройка nginx, SSH-секретов, сервера, миграций и
SQLite описана в [инструкции развёртывания](../../docs/deployment.md).
Общий локальный запуск из корня — `uv run --project platform/api python deploy/run.py` после сборки UI.

При отдельном размещении кабинета на собственном поддомене после `npm ci && npm run build`
и `uv sync --frozen --no-dev` можно использовать
`deploy/throng-dashboard.service`, адаптировав пользователя и пути. Фрагмент
`deploy/nginx.conf` добавляется в отдельный HTTPS server block platform.mutating.tech
и проксирует все пути без переписывания. Основной сайт обслуживается своим виртуальным
хостом. Для публичного входа/регистрации
примените принятые на сервере ограничения частоты запросов.

Также есть отдельный Dockerfile:

```sh
docker build -t throng-dashboard .
docker run --rm -p 127.0.0.1:8001:8001 --env-file /etc/throng-dashboard.env throng-dashboard
```

В Docker укажите `DASHBOARD_API_URL`, доступный из контейнера, например имя
API-сервиса в общей Docker-сети. `127.0.0.1` внутри контейнера означает сам контейнер.

## Проверки

Из `platform/web/`:

```sh
npm ci
uv sync --frozen
npx playwright install --with-deps chromium firefox webkit
npm run build
npm run test:unit
uv run pytest
npm run test:e2e
npm run test:deploy
```

Playwright сам поднимает отдельный настоящий API на порту 18100 и Python-сервис
кабинета на 18101. Тестовые базы уникальны для каждого запуска, лежат в `.runtime/`
и не затрагивают рабочие данные. Для API тесты используют окружение `../api/.venv`,
которое предварительно устанавливается `uv sync --project platform/api --frozen` из корня репозитория.

Функциональные сценарии запускаются в Chromium (desktop и Pixel), Firefox,
WebKit (desktop и iPhone). Проверяются закрытые маршруты, регистрация, ник,
аватар, профиль, организации и роли, пагинация, удаление, RU/EN, темы и сессии.
Сценарии совместного доступа проверяют поиск по email/нику, добавление и удаление
участников, роли и отдельные права, защиту последнего создателя, адресные приглашения
и ссылки, принятие после регистрации, отказ, отзыв и обновление ссылки. Проверяются
ограничения делегирования прав и сохранение форм после сетевых ошибок.
Отдельные сценарии проверяют точные CPU/RAM/free/reserved в личном и общем пулах,
проценты полосок, строки компьютеров, таблицу истории и координаты четырёх линий
с независимыми шкалами CPU и RAM. Резервы создаёт настоящий планировщик API.
Исторические события для проверки графика записываются тестовой фикстурой в БД;
браузер получает их через обычный endpoint API. Тестовый API имеет фиксированную
дату начала истории — 1 января 2026 года; production API не содержит фикстур.

Сетевые сбои воспроизводятся обрывом запросов или отключением сети, без подмены
успешных ответов. Проверяются сохранность введённых ФИ и названия организации,
повторная отправка, блокировка кнопки на время запроса, отсутствие ложных нулей
при ошибке загрузки мощностей и восстановление после обновления страницы данных.
Для проверки восстановления регистрации тестовый API один раз возвращает `503`
при автоматическом входе специального тестового аккаунта после его реального создания.
Серверные тесты также воспроизводят ошибки транспорта и чтения профиля после регистрации.
Тесты серверной границы
дополнительно проверяют зашифрованные cookie и перечень допустимых маршрутов.
Unit-тесты проверяют ступенчатое представление истории и неизвестные интервалы.
HTML-отчёты — `playwright-report/{e2e,deploy,visual}/index.html`, скриншоты и трассы —
`test-results/` с такими же отдельными подпапками.

Для `test:deploy` нужны `nginx` и `openssl` в PATH (`brew install nginx` на macOS,
`apt-get install nginx openssl` на Ubuntu). Тест запускает собственный nginx на
18443 с временным TLS-сертификатом, API на 18210 и кабинет на 18211. Он использует
`deploy/nginx.conf`, заменяя только порт upstream, и проверяет страницы в корне,
ответ `404` для удалённых адресов, deep links, статику, настройки темы/языка, Secure/HttpOnly/Path,
CSRF, отзыв токена при выходе, сохранение сессии после перезапуска кабинета и
восстановление после остановки настоящего API. Системный сервис nginx не затрагивается.
Разделение основного сайта, API и платформы по поддоменам дополнительно проверяется
в `tests/platform/api/deployment/test_native.py` с production-шаблоном nginx.

Визуальные регрессии проверяются отдельно: все страницы, пустые/заполненные пулы,
список участников, форма приглашения, окно прав, просмотр приглашения
и диалог подтверждения, RU/EN, обе темы, desktop/mobile. Эталонные PNG находятся
в `../../tests/platform/web/e2e/visual-snapshots/`. Время и данные фиксированы; отсутствующий эталон
считается ошибкой. Сравнение и обновление выполняются в одном Linux ARM64-образе
с закреплённой версией Playwright и шрифтами (Docker нужен только для этих проверок).
Из корня репозитория:

```sh
docker build --platform linux/arm64 -f tests/platform/web/visual.Dockerfile -t dashboard-visual .
docker run --rm --ipc=host --platform linux/arm64 \
  -v "${PWD}/platform/web/test-results:/workspace/platform/web/test-results" \
  -v "${PWD}/platform/web/playwright-report:/workspace/platform/web/playwright-report" \
  dashboard-visual
```

При намеренном изменении дизайна обновите эталоны и просмотрите diff изображений:

```sh
docker run --rm --ipc=host --platform linux/arm64 \
  -v "${PWD}/tests/platform/web/e2e/visual-snapshots:/workspace/tests/platform/web/e2e/visual-snapshots" \
  dashboard-visual npm run test:visual -- --update-snapshots
```

`npm run test:visual` — команда внутри этого образа: скриншоты с macOS или другого
браузерного окружения нельзя использовать вместо Linux-эталонов. CI запускает
функциональные, серверные, unit, HTTPS и визуальные проверки; последние — отдельной
задачей ARM64. Не пересобирайте `dist/` во время активных браузерных тестов.

При необходимости локально можно явно указать установленный Chromium через
`PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`; в CI используется браузер, установленный Playwright.
